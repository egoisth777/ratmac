## Acceptance criteria

- Pin tamper is detected: in an isolated fixture Run whose Runbook declares a command guard over a pinned gate artifact, mutating the artifact's bytes after the pin causes the next step request to be refused with observed and expected identity, and restoring the pinned bytes lets the same request proceed.
- Guard evaluation builds nothing: evaluating a command guard produces no rebuild of project sources, and a guard command that would require compiling the candidate workspace at evaluation time is rejected as a Runbook validation or pin-time error instead of being silently executed.
- Refusal diagnostics are bounded and present: a deliberately failing guard whose program writes a named-artifact message to stderr yields a refusal containing that message; a program emitting more than the documented bound yields a refusal no larger than the bound plus fixed framing, with a truncation marker; a silent failing program yields a refusal stating that no diagnostic was emitted. Each case is an executable test, including the negative oversize case.
- The freeze is post-integration: in a fixture Run that performs intake integration, the recorded frozen goal revision equals the post-integration content revision of `.arca/current/` and differs from the start baseline revision whenever integration changed the goal; gap-analysis-facing output cites the frozen value, not the baseline.
- Goal drift refuses: after the freeze, editing any `.arca/current/` file causes the next transition request to be refused naming goal drift; reverting the edit clears the refusal. Refused requests leave Scheduler-owned state and transition history unchanged.
- All proofs run in isolated fixture projects through the QA harness; acceptance requires no commit, push, deployment, or global installation.
