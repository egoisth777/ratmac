## Acceptance criteria

- Policy surfaces agree: an executable audit over CLI help output, the root agent protocol, and any present canonical skill or guidance finds the human-approved Main-Agent start policy stated consistently and finds no active user-only or blanket never-agent-start wording; seeding a stale-policy sentence into a fixture copy makes the audit fail (negative), proving sensitivity.
- Engine boundary preserved: code and persisted-schema checks show no caller identity, sign-off token, approval file, authorization service, new Runbook field, or new State File field; start, status, step, and duplicate-start refusal behavior are unchanged by the policy wording change.
- Bootstrap round-trip: from a clean project root, the documented bootstrap command resolves and reports a Stable Engine binary and its identity without touching global configuration or PATH; when a pin record exists and the located binary's hash differs, the bootstrap refuses naming observed and expected identity (negative).
- Doctor honesty: with no active Run, the doctor names the Runbook and state files by role and states the next legitimate action; with an active Run it reports the current phase; in both cases a filesystem snapshot before and after proves it wrote nothing.
- Behavioral sensitivity: role-scenario checks pass on recorded scenarios where the human starts, a signed-off Main-Agent starts once, an unsigned Main-Agent and a Subagent invoke nothing; a deliberately violating scenario record (unsigned Main-Agent invoking start) fails the check (negative); wording-only checks are labeled guidance-consistency in their recorded evidence kind.
- All proofs run via the QA harness in fixture projects or scenario records; acceptance requires no commit, push, deployment, network access, or global installation.
