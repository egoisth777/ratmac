## Acceptance criteria

The implementation may be accepted only when all of the following are true:

- Active SSOT and contributor-facing references consistently call the product `ratmac` and the executable `rtm`; every retained legacy spelling is in the documented historical allowlist.
- Cargo package/library/dependency metadata, QA metadata, source entrypoint, diagnostics, help, fixtures, tests, and regenerated lock/package metadata expose the canonical names, with no unapproved `schd` alias or `arca-scheduler` package surface.
- `rtm start`, `rtm status`, `rtm step`, help, and error paths work end to end with the existing scheduler semantics unchanged; the selected legacy-command policy is deterministic and tested.
- The selected lock-path migration policy preserves arbitration and never silently deletes or bypasses a legacy lock; `.arca/ratmac.toml`, `.arca/state.toml`, and `.arca/log.md` retain their settled data semantics.
- Repository stale-name audit, metadata verification, full tests/QA lanes, formatting, linting, and diff checks pass; this issue's creation step itself performs no implementation, commit, push, or deploy.

## Migration and compatibility decisions required during integration

1. **Command compatibility:** Apply the clean-cutover default: `rtm` is the only shipped executable and `schd` is not retained as an alias. If project owners choose compatibility instead, the accepted goal must define its finite deprecation window, exact forwarding behavior, diagnostics, and tests; an unbounded shim is out of scope.
2. **Package/crate compatibility:** Apply the clean-cutover default: package, library, dependency, and import names become `ratmac`; no duplicate package or re-export solely for the old identity is kept. Any external-consumer migration note belongs in the active docs, not in a compatibility code path.
3. **Persisted data:** Keep `.arca/ratmac.toml`, `.arca/state.toml`, and `.arca/log.md` because they are the settled Machine Class/Run layout and do not encode `arca-scheduler` or `schd` in their names. Do not rewrite state or transition-log contents as part of a branding change.
4. **Transient lock:** Choose and document whether the internal lock path becomes `.arca/rtm.lock` (the clean-cutover default) and how a pre-existing `.arca/schd.lock` is handled after interruption. Never silently delete a lock or bypass arbitration; the selected behavior needs a focused test.
5. **Historical records:** Preserve `.arca/log.md` and archived ticket wording under the working rules. Active references must be canonical; any retained legacy spelling elsewhere must be named in the allowlist and justified as provenance, not treated as a user-facing compatibility surface.
