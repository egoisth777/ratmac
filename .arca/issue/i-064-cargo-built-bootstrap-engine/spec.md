## Evidence and boundaries

- The bootstrap ([rtm.ps1](../../../tools/rtm.ps1)) lists the only places it looks in `function Get-EngineCandidates` (lines 129-135): `target/release`, then `target/debug`, under the root being built. `function Invoke-EngineBuild` (lines 218-250) stamps provenance through `RTM_CHANNEL` and `RTM_SOURCE_COMMIT` (lines 226-229), runs `cargo build --offline --bin rtm` with standard error merged into its output (`2>&1`, line 232), refuses a failed build with "the project-local build did not produce an Engine" (line 238), then takes the first candidate that exists and otherwise refuses with "the build succeeded but no Engine binary is at the expected path", naming `target/debug` (lines 242-248).
- Before building, the main flow reuses the first existing candidate in the stable build checkout (lines 276-281) or in the project root (lines 283-296). It then hashes the binary (line 300), refuses a pin mismatch with "the resolved Engine is not the pinned Engine" (lines 302-312), and prints the `Engine:`, `sha256:`, pin, channel, and `Diagnose:` lines (lines 314-332). Every refusal prints `bootstrap refused:` and its reason on standard error and exits 1 (`function Deny`, lines 52-60).
- The stable build checkout's clean-tree rule counts an untracked `target` or `Cargo.lock` as declared build output and anything else as differing (lines 203-204). A relative `CARGO_TARGET_DIR` would resolve inside the build checkout, where that rule refuses the next run. So would a relative Cargo build folder, which `--target-dir` does not move: in this checkout, `CARGO_BUILD_BUILD_DIR=inter cargo metadata --format-version 1 --no-deps --offline` reports the build folder as the checkout's own `inter` while the output folder stays the configured one, and the bootstrap runs Cargo inside the build checkout (line 230).
- Why a stable build keeps its own `target`: Cargo puts every `rtm` build at `debug/rtm` under its output folder, so under a machine-wide `CARGO_TARGET_DIR` every edition's build checkout and the project root would write one file, and reuse from the Cargo-resolved folder before building (lines 276-281) would hand the stable channel whatever was built last; with no pin recorded, nothing would catch it, breaking the stable build checkout rule (`ELR-002`). The stable bootstrap suite also asserts that "a built engine must sit inside the build checkout" ([t102_stable_bootstrap.rs](../../../test/qa/tests/t102_stable_bootstrap.rs), line 222), and the private bootstrap lane (`t-102`) asserts that "the writes are confined to the build checkout" (`tests/hidden.rs` line 513).
- The bootstrap's own description says "the only paths it may write are the declared build output: target and Cargo.lock" (lines 27-30), which stops being true for a project-root build under a redirect.
- The bootstrap doctor suite ([t045_bootstrap_doctor.rs](../../../test/qa/tests/t045_bootstrap_doctor.rs)) plants the test Engine at a fixture's `target/debug` in `fn prebuild` (lines 70-75) and reads built binaries there (lines 210, 594). Its pin-mismatch test (`fn bootstrap_refuses_pin_mismatch`, from line 275) expects the refusal to name the planted binary's hash (line 307), and `Boot::bootstrap` (lines 78-84) passes the inherited environment, so once reuse follows a redirect that test would see a fresh build instead. The stable bootstrap suite looks in the build checkout's `target/release` and `target/debug` (lines 214-215) and plants a prebuilt binary in `target/debug` (lines 297-299). In scope: both encode the fixed folders.
- The private bootstrap lane (`t-102`) joins `target/debug` for its fixture roots and build checkouts (`tests/hidden.rs` lines 197, 333, 510, 559).
- At filing, an untracked `.cargo/config.toml` in this checkout still sets `[build] target-dir = "E:/cache/hive/cargo/skill-dev/ratmac"` and `cargo metadata` reports that folder, but the folder no longer exists, so the wish's "that folder still holds `debug/rtm.exe`" is stale. The stable build checkout for the newest edition (`edition-009`) reports its own `target` folder. The wish's line pointers (232, 129-135, 246-247) are current. The wish's failed bootstrap run was not repeated, because filing runs no build.
- Out of scope: test helpers such as `today_engine()`, which belong to the test-Engine issue (`i-063-build-message-test-engine`), and the checks inside `rtm doctor`.
- Also out of scope: where the pin is read. The bootstrap reads its pin from `.ratmac/evidence.toml` (lines 301-302), a file the Engine no longer writes now that each Run keeps its own pin in `.ratmac/runs/<id>/evidence.toml`, so real runs always print `Pin: no pin recorded` and never compare. The [live Run pin check issue](../i-074-live-run-pin-check/index.md) (`LRP-001`) carries that fix and supersedes the recorded-pin clause of the bootstrap requirement (`ORS-002`) and the channel pin check (`ECP-002`). Until it lands, this issue proves the wish's "pin-checks" end only in fixtures, so the wish stays open until both issues land. The pins that `SVEV-004` and `SVEV-005` record go wherever the bootstrap reads pins when their ticket lands.

## Assumptions

- Reuse keeps today's order inside the Cargo-resolved output folder: release, then debug, below the build-target folder when one is set.
- The bootstrap asks Cargo only through offline commands from the toolchain it already uses, run inside the build root as the build is, so the build root's Cargo configuration applies: `cargo metadata --no-deps --offline` for the folder and `--message-format=json` on today's build. No new tool or dependency.
- Today's other refusals keep the reasons quoted above. The new refusal names the build root, what Cargo reported or resolved, and the repair. A failed build's guidance prints each `compiler-message` record's `rendered` text, then Cargo's standard error.
- A stable build names its build checkout's own `target` to Cargo as both folders (for example `--target-dir` and `CARGO_BUILD_BUILD_DIR` for that build), so an inherited redirect of either, relative or machine-wide, never mixes editions and never leaves untracked paths in the build checkout. A project-root build whose Cargo-resolved folder lies outside the project root builds first, so it never takes a binary another build root left there. This narrows today's reuse for that one case; reuse inside the project root and inside a build checkout stays.
- Fixture checks give each fixture its own output folder, so no two tests share one. The doctor suite's planted-binary tests set `CARGO_TARGET_DIR` to the fixture's own `target` and clear `CARGO_BUILD_TARGET` for the bootstrap they start, so no inherited redirect or Cargo configuration file moves their output.
