# Ticket: t-129 — authorized review transitions

## Vertical Outcome

A review-governed Run changes State only after the Engine verifies the required independent group reviews and its designated Approver's authorization of the exact fresh transition intent. Unknown signers, a group member without approval authority, a contributor's unsigned claim, missing review, changed work, altered policy, and replay all refuse before state, verdict consumption, or history mutation. Both ordinary and blocked transitions obey the same rule; reviewer roles remain distinct from mechanical guards.

## Observable Output

Defined before implementation. The public checks and the private lanes both
judge this shape; neither needs the other's arrangement or the source. Every
sentence below is observable through the process exit code, stdout/stderr
bytes, files under the Engine root, or the operation log the crate feature
`test-fault-injection` writes. Paths in messages use the Engine's one
displayed spelling (forward slashes); `<Engine root>` below is that spelling
of the resolved shared `.ratmac/`.

**Terms.** A *review policy* is the pinned set of facts a Machine Class
declares in a `review` table: the reviewer labels with their public keys, the
designated Approver, the minimum count of distinct reviews, whether the
Approver may also supply one review, the digests of the pinned verifier and
the allowed-signers file, and the explicitly addressed enrollment manifest.
A *governed Run* is a Run whose pinned Machine Class - the top-level class
for a top-level Run, the recorded child class for a ledger-recorded child -
declares a review policy; governance is fixed by the runbook pin recorded at
admission, so a Run admitted under a runbook with no `review` table stays
ungoverned for its whole life even if a later runbook declares one, and no
surface ever reports such a Run as reviewed. The *builder actor* is the
operating-system identity running the Engine, rendered `DOMAIN\name` on
Windows and the account name of the effective uid on Unix. An *enrollment
manifest* is the operator-written TOML file the declaration addresses; it
binds the project scope, the builder actor and every key enrolled to it, the
reviewer label/key set, the Approver, the minimum count, the permitted role
combination, and the verifier and allowed-signers paths with their SHA-256
digests. A *protected path* is a file, and every ancestor directory, that the
builder actor cannot write, delete, replace, take ownership of, or re-permit:
Unix - owned by root with no builder, group, or other write permission along
the path; Windows - owned by `NT AUTHORITY\SYSTEM` or `BUILTIN\Administrators`
with the effective builder token denied write, delete, ownership, and
permission change along the path, no reparse point anywhere on the path, and
no elevated builder token. The *canonical intent* is the exact byte string
defined below; a *review signature* is a detached OpenSSH Ed25519 signature
over it under namespace `ratmac-review-v1`, an *approval signature* the same
under `ratmac-approve-v1`. The *authorization sequence* is the per-Run,
Engine-owned counter of accepted authorizations. The *work digest* is the
SHA-256 computed exactly as the legacy goal revision is
(`src/goal.rs:205-221`, `legacy_revision`):
every file under the declared `work` paths, collected recursively and
sorted by displayed relative path, hashed as relative-path bytes, one LF,
the file's bytes, one LF; a declared path that is neither file nor
directory refuses with the goal-freeze family's read error; with no `work`
declared the empty input is hashed.

**The declaration.** A runbook carries at most one top-level `[review]`
table; a `classes.<name>` body may carry at most one `review` table with the
same shape. Fields: `manifest` (string, an absolute path), `policy-digest`,
`verifier-digest`, `signers-digest` (each 64 lowercase hex), `minimum-reviews`
(integer >= 1), `approver` (string), `approver-may-review` (boolean, optional,
default `false`), `work` (optional array of unique non-empty
repository-relative paths that lexically stay inside the repository), and
`[[review.reviewers]]` entries each with exactly `label` (non-empty, unique)
and `key` (one OpenSSH public-key line: `ssh-ed25519`, one base64 body that
decodes to an Ed25519 key, optional trailing comment). The *policy digest* is
the SHA-256 of `ratmac-policy-v1`, one NUL byte, then the length-framed
fields in order - Approver label, `minimum-reviews` in canonical decimal,
`approver-may-review` as `true`/`false`, then each reviewer sorted by label
as framed label then key - so any change to membership, roles, or count
changes it. An unknown key inside a `review` or `reviewers` table refuses
with today's unknown-key rule (`RB103`, `src/machine.rs:1306`). Semantic
defects refuse at parse carrying new codes in today's code position, detail
`invalid review declaration: <detail>`, rendered by each loader through
exactly today's runbook-parse path (`src/scheduler.rs:868-871`): `rtm step`
and `rtm status` as stderr `rtm: <command>: parse .ratmac/ratmac.toml
[RB7xx]: invalid review declaration: <detail>` plus today's next line,
exit 1; `rtm hold` as `rtm: hold refused; parse .ratmac/ratmac.toml [RB7xx]:
invalid review declaration: <detail>`, exit 1; `rtm start` as `rtm: start:
parse .ratmac/ratmac.toml [RB7xx]: invalid review declaration: <detail>`
and `rtm spawn` as `rtm: spawn: parse .ratmac/ratmac.toml [RB7xx]:
invalid review declaration: <detail>`, each exit 1 with no next line; and
`rtm doctor` reports each defect as an error finding bearing its code,
exiting 2:

| Code | Detail text after `invalid review declaration: ` |
| :--- | :--- |
| `RB701` | the table or a scalar field is malformed: not a table, a key of the wrong type, `manifest` not an absolute path, a digest that is not 64 lowercase hex, `minimum-reviews` below 1 or not an integer, `approver-may-review` not a boolean. |
| `RB702` | the reviewers list is malformed: not an array of tables, an entry without exactly `label` and `key`, an empty or duplicate label, a malformed key line, or the same key bytes under a second label (`the same public key appears under labels "a" and "b"`). |
| `RB703` | `approver` is missing or names no declared reviewer (`approver "x" names no declared reviewer`). |
| `RB704` | `minimum-reviews N exceeds the M distinct reviews the declared roles can supply`, where M is the reviewer count less one when `approver-may-review` is `false`, else the reviewer count. |
| `RB705` | a `work` entry is empty, duplicated, absolute, or lexically escapes the repository. |

`.arca/runbook-spec.md` grows this table and the code rows in the same
landing, so the specification/code parity check stays green; `rtm scaffold`
output and every existing fixture declare no `review` table and change
nothing.

**The enrollment boundary.** At every admission (`rtm start`; `rtm spawn`
minting a child whose class declares review) and at every verification
(`rtm step`, `rtm hold`, `rtm intent` on a governed Run) the Engine reads the
addressed manifest and refuses before any write when: it is missing or
unreadable (`the enrollment manifest <path> is missing or unreadable`); it or
the allowed-signers file is not a protected path (`the enrollment manifest
<path> is not protected against the builder actor <actor>` - the same shape
names the signers file: `the allowed-signers file <path> is not protected
against the builder actor <actor>`; either holds when the file or any ancestor
directory fails the protection rule, and nothing follows `<actor>`); the path carries a reparse point or the process
token is elevated (`the enrollment path <path> cannot be verified as
protected: <fact>`); the manifest's `builder.actor` differs from the actual
process identity, its `project-scope` differs from the canonical path of the
resolved primary checkout (the primary checkout the invoking checkout
resolves to under the t-119 one-root rule, forward slashes; the invoking
checkout itself without Git) - the canonical path is the platform's
canonicalized path rendered with forward slashes, on Windows its `//?/`
prefix included, the spelling the Engine already keys a project by, compared
byte-for-byte - its reviewer set, Approver, counts, or
role combination disagree with the declaration, any enrolled builder
key appears among the reviewers or as the Approver (`the reviewer "x"
carries the builder's enrolled key`, `the approver "x" carries the
builder's enrolled key`), the recomputed policy
digest differs from the declared one (`the declared policy digest <a> does
not match the recomputed <r>`) or, the two agreeing, from the enrolled one
(`the declared policy digest <a> does not match the enrollment's <b>`), or a
verifier or signers digest differs, checked in this order: the verifier
file's actual SHA-256 against the enrollment's binding (`the verifier at
<path> hashes <a>, the enrollment binds <b>`), the declared
`verifier-digest` against that binding (`the declared verifier digest <a>
does not match the enrollment's <b>`), then the same two for the signers
file (`the allowed-signers file at <path> hashes <a>, the enrollment binds
<b>`; `the declared signers digest <a> does not match the enrollment's
<b>`). In these details the manifest `<path>` is the declaration's `manifest`
string byte-for-byte, and a verifier or signers `<path>` is the bound path
with forward slashes. Each detail is one shared string; the renderings below
compose it. Where this contract quotes no detail text (the builder-actor,
project-scope, and reviewer-set disagreements; a malformed manifest; the
`RB701` and `RB705` details; the `rtm intent --out` refusals), the detail is
the implementation's own single line and checks pin only the frame and code
around it.
There is no environment override, no self-enroll verb, and no flag: a
governed workflow without its independent trust anchor refuses, and the
Engine never generates a substitute identity, key, or manifest.

**The enrollment manifest grammar.** Strict TOML; an unknown, missing, or
mistyped key makes the manifest malformed, which refuses with a detail
naming its path. Top-level keys: `project-scope`, `policy-digest`,
`minimum-reviews`, `approver`, `approver-may-review`, `verifier-path`,
`verifier-digest`, `signers-path`, `signers-digest` (each with the same type
and digest shape as the declaration's field of that name; paths absolute);
one `[builder]` table with exactly `actor` (string) and `keys` (array of
OpenSSH public-key lines, possibly empty); and one `[[reviewers]]` row per
reviewer with exactly `label` and `key`, the declaration's shapes.

**Canonical intent bytes.** `ratmac-authorization-v1`, one NUL byte, then
each field as its unsigned 64-bit big-endian byte length followed by its
UTF-8 bytes, in this fixed order: purpose (`step` for an ordinary
transition, `hold` for a blocked one - the same word in the review and the
approval intent, in `rtm intent`'s stdout, and in the archive record's
`purpose`), project scope (the spelling above), Run id, owning
class (`runbook` for a top-level Run, the class name for a child), workspace
(canonical, forward slashes), binding digest (length-framed sorted
`name=value` pairs of the recorded bindings; empty for a top-level Run),
next authorization sequence (canonical decimal, no leading zeros), hold
occurrence (empty), held-record digest (empty), current State, target State,
input (the selected transition input for a branching State; else empty),
blocker (the exact `--blocker` reference for a hold; else empty), Engine
identity (the running executable's SHA-256), runbook identity (the pinned
runbook SHA-256), goal identity (the recorded
`[goal] frozen` revision once frozen, else the recorded `[goal] baseline`,
else empty - `src/pin.rs:55-57`; the recorded string byte-for-byte, a
portable revision's `v2:` prefix included), policy digest, enrollment digest (SHA-256 of the exact
manifest bytes), builder actor, current work digest, previous amendment
digest (empty), proposed-authority digest (empty), change-set digest (empty),
review-set digest. Inapplicable fields are empty, never omitted. The
review-set digest is the SHA-256 of `ratmac-review-set-v1`, one NUL byte,
then for each review sorted by label the framed label and the exact
signature-file bytes; it is empty in a review-signature intent and computed
in the approval intent the Approver signs.

**Exposing the intent: `rtm intent`.** A new read-only verb joins the one
public route table (`Commands:` gains `intent` after `hold`). Forms:
`rtm intent --run <id> --out <path>` renders the review intent for the
ordinary transition the current State and live verdict select;
`rtm intent --run <id> --hold --blocker <ref> --out <path>` renders the
blocked intent; adding `--review <label>:<sig>` options (the same pairs
`rtm step`/`rtm hold` will receive) renders the approval intent with the
review-set digest computed over those files. Addressing refusals reuse
today's texts with the command name `intent` (`rtm: intent: run id "run-005"
is not an exact roster member; runs: <summary>` plus rows and the next line,
exit 2 - `src/cli.rs:166-215`,
`src/scheduler.rs:991-1002`). Operational
refusals are stderr `rtm: intent refused; <detail>`, exit 1: an ungoverned
Run (`run <id> resolves in no review-governed class; the canonical intent
exists only under a declared review policy`), a missing `--out`, an `--out`
path inside the Engine root or an existing directory, a missing or invalid
live verdict on a branching State (today's verdict refusal detail), an
authorization archive that will not parse, and the enrollment details
above. `rtm intent` keeps the WEB-004 prelude, so a residue refusal is
`rtm: intent: <today's residue detail>`, exit 1; a terminal Run, an
already-blocked Run addressed without `--hold`, and `--hold` without
`--blocker` refuse with today's step/hold refusal details under
`rtm: intent refused; `, exit 1; hard errors render as `rtm: intent:
<error>` plus today's next line, exit 1; operational refusals carry no
next line. `rtm intent --help` prints `Usage: rtm intent --run <id>
[--hold --blocker <ref>] [--review <label>:<sig>]... --out <path>
[--help]` followed by one paragraph naming the review, approval, and
blocked forms. On success `--out` receives the whole canonical bytes in
one step (temporary sibling plus rename, so a reader that finds the file
reads all of it), the Run lock is taken for the render (a held lock
waits under today's 5 s deadline - `src/lock.rs:37` - then refuses
`rtm: intent: lock wait expired: <path>; <owner-token diagnostic>`
unchanged, `src/lock.rs:514`), nothing
under the Engine root is written, and stdout is one LF-terminated line,
exit 0: `rtm: canonical <purpose> intent for run <id> written to <out>
(sha256 <hex>)`, where `<out>` is the `--out` argument exactly as given in
the displayed spelling (backslashes as forward slashes, never canonicalized
or made absolute) and `<hex>` is the SHA-256 of the written bytes.

**Authorized `rtm step`.** For an ungoverned Run every byte is unchanged.
For a governed Run the existing order holds - residue preflight, addressing,
runbook parse and pin, Run lock, guard evaluation, verdict validation, route
selection, all with today's texts - and then one new verification boundary
runs under the already-held Run lock, immediately before consumption, in this
order, the first failure refusing: enrollment and agreement (details above);
signature options - `--review <label>:<sig>` repeatable, `--approve <sig>`
exactly once - with a governed Run lacking them refusing `authorization:
signatures: observed none; expected <n> distinct review signature(s) and one
approval signature over the canonical intent (rtm intent --run <id>)`; a
duplicate review label refusing `authorization: reviews: observed label
"label" given twice; expected each enrolled reviewer at most once`; a
submitted approval whose SHA-256 equals an archived record's
`approval_signature_sha256` refusing `authorization: replay: observed
the approval already consumed as sequence <n> under
<Engine root>/runs/<id>/authorizations/; expected a fresh authorization at
sequence <n+1>`; each review verified with the pinned
verifier (`ssh-keygen -Y verify -f <signers> -I <label> -n
ratmac-review-v1 -s <sig>` with the recomputed canonical bytes on standard
input, judged by exit status only - `check-novalidate` is never invoked), a
failure refusing `authorization: review: observed a signature at label
"label" that verifies under no enrolled reviewer key; expected a
ratmac-review-v1 signature by an enrolled reviewer`; the distinct count
refusing `authorization: reviews: observed <k> distinct accepted review(s);
expected at least <n>`; a review by the Approver under a policy that does not
permit it refusing `authorization: reviews: observed a review by the
approver "label"; expected reviews by members other than the approver`;
approval attribution - verified first under the designated Approver, and on
failure under every other enrolled label - refusing `authorization:
approval: observed a signature by member "label"; expected the designated
approver "label"` or `authorization: approval: observed a signature by no
enrolled identity; expected the designated approver "label"`; and approval
verification against the recomputed intent refusing `authorization:
approval: observed a signature that does not verify against the recomputed
canonical intent sha256 <hex>; expected a fresh approval of that exact
intent (rtm intent --run <id>)`. An enrollment-and-agreement detail composes
as the sub-boundary `enrollment`: `authorization: enrollment: observed
<detail>; expected the enrolled trust origin`. Every authorization refusal is one
`StepOutcome::Refused` failure: exit 0, stdout `rtm: step refused;
authorization: <sub-boundary>: observed <observed>; expected <expected>` on
one LF-terminated line followed by today's `next: rtm step --run <id>`
(`src/scheduler.rs:241-267`, `src/cli.rs:446-452`, `src/teach.rs:35-43`), and
writes nothing: Run Record, evidence, live and archived verdicts, ledger,
history, mint, and any authorization archive stay byte-identical. Passing
`--review`/`--approve` on an ungoverned Run refuses at argument validation,
exit 2: `rtm: step: --review and --approve address no declared review
policy`. The same options ride `StepRequest` so `Scheduler::step` and
`cli::run_from` keep their parity. Both usage strings grow the options
(`src/cli.rs:65-71`): `rtm step --help` renders `Usage: rtm step --run
<id> [--review <label>:<sig>]... [--approve <sig>] [--help]`, and
`rtm hold --help` gains the same two options after
`--confirm "hold <id>"`; the descriptions otherwise stand. A successful
governed step prints exactly what today's success prints (the successor
State's prompt and the existing next line), exit 0.

**Durable order and recovery for `rtm step`.** With authorization accepted,
the durable steps are exactly today's plus one, in order: (1) the live
verdict is archived (today's consumption point, straight-line steps skip
it); (2) the accepted authorization is archived to
`<Engine root>/runs/<id>/authorizations/<nnnnnn>.toml` - the next
zero-padded sequence past the highest existing index, one strict-TOML record
holding `sequence`, `purpose`, `intent_sha256`, `policy_sha256`,
`enrollment_sha256`, one `[[reviews]]` row per accepted review (`label`,
`signature_sha256`), `approval_signature_sha256`, `from_state`, `to_state`,
and `origin` (`host-enrolled`, or `test-injected` under the seam below) -
written whole in one step and never rewritten or deleted except by the
Engine's own rollback; (3) the goal-freeze evidence, when the transition
freezes; (4) the successor Run Record replace; (5) the history append. The
Run lock is held from guard evaluation through step (5). A refusal, fault,
or kill before (2) leaves the pre-transition state and the same signatures
still valid at the same sequence. A kill after (2) and before (4) leaves the
Run Record at the old State with the authorization archived: the sequence
number is spent (monotonic, never reused), the retry needs a fresh verdict
where one was consumed and a freshly rendered and signed intent at the next
sequence - `rtm intent` renders it - and the archived record stays as
truthful history. A graceful failure at (3), (4), or (5) rolls back (2) and
(1) exactly as today's machinery restores the archived verdict and evidence
(`rollback_transition_after_append_failure`,
`src/scheduler.rs:2607`), so
the pre-transition bytes return and the same sequence is offerable again; a
restore failure keeps today's refusal families, naming the authorization
archive beside the other artifacts. After (4) the transition is committed
with today's deliberate State-first interruption limit unchanged: a death
before (5) leaves a true transition with no history line, never a false
one. A completed transition consumed its authorization: replaying the same
signature files meets the replay refusal above, and any later transition of
that Run needs a fresh intent at the next sequence.

**Authorized `rtm hold`.** A governed Run holds through the same boundary.
`rtm hold --run <id> --blocker <ref> --confirm "hold <id>" --review
<label>:<sig> ... --approve <sig>`: the plan's existing checks (residue,
addressing, confirmation phrase, blocker beneath a declared root, terminal
and already-blocked refusals - all today's texts, `src/blocked.rs:209-291`)
run first, then the full verification boundary of `rtm step` above, and
`apply` re-verifies the recomputed intent under the Run lock before the
first write, refusing a stale plan exactly as today. Every authorization
refusal is stderr `rtm: hold refused; authorization: <the same detail
strings>`, exit 1, writing nothing. Durable order: authorization archive
(the same per-Run sequence space `rtm step` uses), then today's paused
Run Record write, then today's history append, with the existing
all-or-none rollback extended to remove an archived authorization it just
wrote. A kill after hold's authorization archive and before its record
write leaves the Run unblocked with the sequence spent - exactly step's
rule; the retry renders a fresh hold intent at the next sequence. Success
stdout is unchanged: `rtm: run <id> paused against <blocker>;
routed <from> -> <to>` and `The Run is not passed; a human resumes it when
the blocker clears.`, exit 0. `--review`/`--approve` on an ungoverned hold
refuses `rtm: hold: --review and --approve address no declared review
policy`, exit 2.

**Admission refusals.** `rtm start` on a runbook whose top-level class
declares review, and `rtm spawn` minting a child whose class declares
review, verify the enrollment boundary before the ignore-policy step and
before any mint or ledger write, refusing with the shared details above:
`rtm: start: the runbook declares a review policy; admission requires its
enrolled trust origin: <detail>`, exit 1; `rtm: spawn: spawn refused: the
class "name" declares a review policy; admission requires its enrolled
trust origin: <detail>`, exit 1 - both writing nothing, advancing no mint
counter. `rtm spawn` from a governed parent needs no signatures (the
parent's State does not change); `rtm respawn` and `rtm abandon` need none
(retirement is not a State change). A governed successor class meets the
admission check at respawn's validation stage, before t-122's record step
takes any lock or reserves the ordinal, so before any ledger append,
retirement, or admission write - refusing
`rtm: respawn refused; the class "name" declares a review policy;
admission requires its enrolled trust origin: <detail>`, exit 1, writing
nothing, advancing no mint counter, leaving the predecessor live.
`rtm status`, `rtm doctor`, history views, and the roster change no byte
for governed or ungoverned Runs, report no review fact about a Run that
did not authenticate one, and `rtm doctor` adds only the `RB70x` findings
above.

**Operation log.** With `test-fault-injection` and
`RATMAC_TEST_OPERATION_LOG` set, this contract adds no operation kind: only
`roster`, `record`, `ledger`, `runbook`, `blocker`, `target`, and `lock`
appear (`src/observe.rs:7-9`). An ungoverned invocation logs exactly what it
logs today. A governed `rtm step`/`rtm hold`/`rtm intent` adds `target`
marks at the enrollment, verifier, and signers validation boundary and one

`rtm start`, `rtm spawn` minting a governed child, `rtm respawn` admitting
a governed successor - logs the same `target` marks at its enrollment,
verifier, and signers validation boundary, before the first mint or ledger
write and before the first `lock` line; a refused admission logs only the
boundaries it reached. Ungoverned invocations are unchanged.
