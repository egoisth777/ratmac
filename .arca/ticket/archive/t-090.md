# Ticket: t-090 — Deliberate damage refuses on an uncommitted tree

## Vertical Outcome

The safety-commit rule stops being prose. A command-class guard on the step into the
deliberate-damage stage observes whether the working tree holds an uncommitted change to a
tracked file. When it does, the step refuses, names the observed fact against the expected one,
and leaves State and Status untouched; committing the change makes the same step succeed.

## Worktree Scope

- **Included:** the guard declaration and its refusal path exercised end to end, plus whatever
  the command-class guard needs to report the observed-against-expected pair in its bounded
  diagnostic rather than as raw command output. QA coverage in
  `test/qa/tests/t090_damage_checkpoint.rs` and six private lane checks.
- **Why now:** the rule has already failed once in practice — a composition-format turn
  destroyed a tracked file by restoring stale index bytes — and the guard class that can enforce
  it is already in the closed vocabulary.
- **Excluded:** no new guard kind is introduced. A file that was never added stays invisible to
  an exit code; that limit is recorded in `ADR-0015` and needs the repository-state guard kind
  steering carries as deferred debt. The damage step's own evidence rules are unchanged.
- **Expected merge/output:** on a clean tree the step behaves exactly as before; on a dirty one
  it refuses without writing.
- **Superseded-test fate:** none superseded. Any suite that steps through a damage-shaped stage
  on a deliberately dirty fixture is updated to commit first, and must state why in its own
  comment so the change is not mistaken for weakening the guard.
