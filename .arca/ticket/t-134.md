# Ticket: t-134 — safe nested invocations

## Vertical Outcome

A declared nested invocation executes a pinned child program using a separate Engine root and returns, through the parent's dedicated captured pipe from the pinned child Engine endpoint, an Engine-produced terminal receipt bound to that invocation, child Run, class pin, Engine identity, and terminal outcome. The parent advances only on the current child's verified successful terminal receipt; process exit zero, skill-wrapper output, agent-authored receipt files or markers, stale/replayed receipts, failed/held/nonterminal Runs, and mismatched roots or identities cannot pass it. No level reads or writes another level's runtime state as its own. The Engine propagates and validates lineage across nested program boundaries; a repeated declared program/class identity, repeated canonical Engine root, malformed inherited lineage, or maximum-depth overrun refuses before invoking or admitting the child and names the offending lineage. Distinct programs with distinct roots may use the same Engine executable; its digest authenticates the executable and is not a recursion identity. This lineage boundary governs cooperating pinned programs and does not claim to prevent a hostile program from discarding its environment and launching an unrelated top-level process. Ordinary same-root spawn remains its existing one-level composition model, distinct from independently rooted program calls.

**Terms.** A *program* is one ratmac-powered project: a checkout holding its
own `.ratmac/ratmac.toml` and resolving to its own Engine root. A *declared
program identity* is the non-empty string a runbook carries in its new
optional top-level `program` key; it is the identity lineage compares, and it
is never derived from a path or a digest. A *canonical Engine root* is the
`fs::canonicalize` spelling of a project's resolved Engine root, rendered
with forward slashes (`src/root.rs:467-480`) and the verbatim prefix kept, so
on Windows it begins `//?/` exactly as t-129's recorded roots read
(`test/qa/tests/t129_authorized_review_transitions.rs:57`; the `E:/x` in the
refusal examples below is illustrative); two checkouts of one repository -
including two linked worktrees - share one canonical Engine root
(`src/root.rs:33-61`), so "distinct root" means distinct canonical Engine
root, never a distinct spelling. An *invocation lineage* is the ordered list
of (declared program identity, canonical Engine root) pairs of the programs
in one nested call chain, including the level being entered, newest last -
so the last entry is always the launched program's own; its *depth* is its
entry count. A *nested invocation* is one execution of a `nested_run` guard:
the parent Engine launches the *child Engine protocol endpoint* - the same
executable the parent runs, addressed by the new route `endpoint` - in the
child checkout. An *invocation address* is the Engine-minted string
`<parent run id>-inv-<n>`, `<n>` rendered exactly as mint ordinals are
(three-digit zero-padding, wider past 999 unpadded, `src/mint.rs:70`). The
*dedicated receipt pipe* is an OS pipe the parent creates for one invocation;
the parent owns the read end and passes only the write end to the endpoint
process; the endpoint writes the *terminal receipt* - the strict envelope
below - to that write end and nothing else ever touches it. A *driver* is
the optional program the parent's declaration names to drive the child Run's
allowed work; it runs in the child checkout without the receipt pipe. A
*governed child* is a child whose pinned runbook declares a review policy
under the t-129 terms as landed (policy digest `src/review.rs:412-415`,
enrollment boundary `src/review.rs:620-687`, authorization archive
`src/review.rs:1969-1971` and `:2073`); every other child is *ungoverned*.
The *nested ledger* is the parent-owned, append/annotate-only file
`<parent Engine root>/runs/<parent>/nested-ledger`, mechanically identical to the spawn
ledger (`src/ledger.rs`): prior bytes stay a prefix, an annotate touches
exactly one field inside exactly one entry, and reads are strict. Its
entries are `[[invocations]]` blocks rendered the way the spawn ledger
renders `[[children]]` (`src/ledger.rs:327-348`: one `key = value` line per
field, strings as TOML basic strings through the same escaping, one blank
line closing each block), fields in this order: `invocation`, `program`,
`root` (the declared spelling), `canonical_root`, `from_state`,
`parent_sequence` (a canonical-decimal string), `engine_pin`, `class_pin`,
`receipt_sha256`, `child_run`, then the boolean `consumed`. An
*invocation record* is the child-owned strict TOML file `<child Engine
root>/runs/<child>/invocation.toml` binding one invocation address to one
child Run. A nested-ledger entry is *consumed* when its `consumed = true`
mark is flipped in the commit stage below, and *current* when it is
unconsumed, its recorded `from_state` equals the parent Run's current State,
and its recorded `parent_sequence` equals the live count of transition-log
records naming the parent Run; every other unconsumed entry is *stale*.

5. **Mint or resume the invocation.** Find the guard's candidate entry: the

   the canonical child root, `from_state` (the parent's current State),

   and empty `class_pin`, `receipt_sha256`, `child_run`, plus
   `consumed = false`. A minted ordinal is never reused; a failed append
   leaves the ledger exactly as it reads.
6. **Launch the endpoint** in the child checkout: `rtm endpoint
   --invocation <address> --lineage <lineage hex> --receipt-fd <n>`,
   stdin null, stdout and stderr piped and captured, the environment

   grammar's transport form below), and the pipe's
   write end as the only non-standard descriptor passed. `<n>` is that
   descriptor's raw platform value in unsigned decimal - the file
   descriptor number on Unix, the handle value on Windows, where the
   Engine marks the write end inheritable for this launch alone through the
   `windows-sys` `Win32_Foundation` feature `Cargo.toml` already enables -

   identity equals the declared one; the canonical root equals the
   pre-launch resolved one; the child Run id equals the entry's recorded

   recorded now when both are empty (a later differing value refuses); the
   engine identity equals the pinned digest; the governance fields obey the
   governed-child rule below; and the outcome is `passed` (anything else:

   value>`, as the outcome row reads, `<field>` spelled exactly as the
   receipt envelope's field list below names it (`invocation address`,
   `program identity`, `canonical child root`, `child Run id`, `class pin`,
   `engine identity`, `outcome`) and each value as its envelope string.

The child Engine is the only writer of this envelope, and only after

   `class-pin`, and `engine` (the endpoint's own executable SHA-256). It
   sits inside `runs/`, so the t-121 ignore policy already covers it and
   the policy bytes change not at all.
5. **The driver.** When the parent's declaration names one, launch it in
   the child checkout with cwd there, stdin null, stdout and stderr piped
   to the endpoint (captured, bounded by `DIAGNOSTIC_BOUND`), the inherited
   environment - `RATMAC_LINEAGE` included, so a grandchild's chain
   propagates - and without the receipt pipe: the pipe is not among the
   descriptors the driver or any of its descendants receive, and a driver
   that writes to every descriptor it can open cannot reach it. Absent a
   driver, the child Run waits for external motion - a human or agent
   running ordinary child-side commands. On resume the driver is
   re-launched whenever the recorded Run is not yet terminal.
6. **Terminal fact.** Wait until the child Run's record reads a terminal
   status (`passed` or `failed`), the driver having exited first when there
   is one; a driver exiting zero without a terminal child Run refuses
   (`the driver exited 0 while run <id> is <status> at <state>; diagnostic:
   <bounded driver output>`), and a driver exiting nonzero refuses
   likewise. A child Run paused by `rtm hold` (t-130: `status = "blocked"`,
   a pause record under `runs/<id>/pauses/`, a journal under
   `runs/<id>/journal/`) is not terminal: the wait continues until a human
   resumes it - `rtm resume --run <id>` by typed confirmation and blocker
   reference, plus one `ratmac-resume-v1` signature when the child is
   governed - and a held parent never reaches this guard at all, because
   `rtm step` refuses a held Run before guard evaluation (`rtm: step
   refused; held: observed run <id> is paused against <blocker> (status
   blocked); expected a resumed Run (rtm resume --run <id>)`,
   `src/scheduler.rs:4003-4022`). A child Run retired by human abandonment
   is terminal as `abandoned`: its directory keeps only `spawn-ledger`, the invocation
   record is gone with the rest, and an endpoint that read the record
   before the retirement emits outcome `abandoned` carrying the run id it
   recorded at admission - the named resumable child outcome. For an
   ungoverned child the parent's step 7 refuses that receipt as a
   non-`passed` outcome; for a governed child the endpoint emits outcome
   `abandoned`, governance `governed`, the policy and enrollment digests,
   and an empty terminal authorization digest, and the parent's governance
   check - which precedes the outcome check - refuses it, never inventing
   completion.
7. **Read back, then emit.** Re-read the terminal record from disk, count
   the child's transition-log records naming the Run, and only then write
   the whole envelope to the receipt pipe in one write, close it, and exit
   0 with stdout and stderr empty. The endpoint's success is silent;
   everything it owes is on the pipe.

**Lineage grammar.** `ratmac-lineage-v1`, one NUL byte, then the entry count
as unsigned 64-bit big-endian, then per entry two length-framed UTF-8
strings: the declared program identity and the canonical Engine root,
forward slashes. Trailing bytes, a count below two in any inherited or
endpoint-received chain (the launching parent's entry and the launched
program's own must both be present), or a frame that stops mid-field is
malformed; the display form for refusals is the ` > `-joined
`<identity>@<root>` chain above. Both carriers - the `--lineage` argument
and `RATMAC_LINEAGE` - hold these bytes as lowercase hexadecimal, two digits
per byte and nothing else, because argv and the environment cannot carry a
NUL byte; a carrier that is empty, of odd length, or holds a character
outside `0-9a-f` is malformed before its bytes are parsed. Agreement
compares the two hex strings; refusals render the display form, never the
hex.

**Recovery - each durable step, and the retry.** The durable steps are P1
the nested-ledger append; C1 the child Run directory followed at once by
its invocation record; C2 the remaining admission artifacts
(`evidence.toml`, the reserved `spawn-ledger`, `run.toml` last); C3 the
driver launch; C4 the child's own terminal write (today's step machinery);
C5 the receipt write; P2 the parent's annotate; P3 the consumed flip.
`rtm step --run <parent>` is the retry verb and is idempotent:

| State found | The retry |
| :--- | :--- |
| No nested-ledger entry (killed before P1) | Fresh mint, launch, normal flow. |
| Entry current, no child Run (killed after P1) | Resume: launch the endpoint with the entry's address; the endpoint admits, records, drives, and emits. |
| Child Run directory created, invocation record absent (killed inside C1's one-write window) | The orphan directory is unadmitted and roster-invisible (no `run.toml`); the retry finds no record and mints a fresh child Run. The interrupted ordinal stays reserved and is never reused, so no second admitted child can exist. |
| Invocation record durable, Run not yet admitted (killed between C1 and C2) | Resume: the endpoint's scan finds the record, completes that same Run's admission - same id, restartable - and proceeds. |
| Child admitted and recorded, not terminal (killed at/after C2) | Resume: same Run, driver re-launched, terminal awaited, receipt emitted. |
| Child terminal, receipt undelivered or unverified (killed at/after C4/C5/P2) | Resume: the endpoint re-reads the terminal fact and re-emits the same envelope; the parent re-verifies byte-for-byte, the annotate is a no-op, the guard passes. |
| Entry current, a different invocation's receipt arrives (replay) | Step 7's address mismatch refuses; no transition. |
| Entry consumed, the guard evaluated again (a later cycle) | Mint a fresh invocation and a fresh child Run; the older result cannot be borrowed. |
| Entry stale (the Run's history grew or its State moved - a hold, another transition, the crash window after the Run Record replace) | Not resumed; the next evaluation mints fresh. |
| Child retired by human abandonment | The named resumable outcome. An endpoint that witnessed the retirement emits the `abandoned` receipt and the parent refuses it - at the outcome check for an ungoverned child, at the governance check for a governed one; once the record is gone, a retry's scan finds no record and the next evaluation mints a fresh child. |

**Concurrency.** Two `rtm step` invocations of one parent serialize on the
addressed Run lock, exactly as today; the second finds the first's outcome
recorded and decides from the recovery table. The parent never holds the
root lock across a nested wait, the child's locks live under the child's
root, and shared roots and recursion were refused before launch, so no lock
cycle exists. Nothing deadlocks with a nested wait: the boundary holds no
root lock and the child's locks live under the child root. `rtm spawn`,
`rtm hold`, `rtm resume`, `rtm recover`, and `rtm abandon` addressing the
waiting Run contend on its Run lock - held by the nested wait - and refuse
at today's 5 s deadline with
today's `lock wait expired: <path>; <owner-token diagnostic>`
(`src/lock.rs:649-653`, the 5 s deadline `src/lock.rs:37`), writing
nothing; `rtm start`, root-domain work, and
operations on other Runs are unaffected. A governed child's admission
serializes on the child root's own locks under the child's root-lock-first
rules, unchanged.

**Operation log.** With `test-fault-injection` and
