# Ticket: t-146 — repeated run refusal

## Vertical Outcome

Every command that addresses a Run with `--run` (`status`, `step`, `intent`, `hold`, `resume`, `recover`, `spawn`, `respawn`, `abandon`) refuses `--run` given more than once, whether the values match or differ, and acts on none of them. It exits 2 with a message starting `<command>: --run given twice; address exactly one run; ` followed by the Run roster exactly as that command prints it when `--run` lacks a value; `abandon` keeps today's longer form. Before refusing it reads only what its roster output needs, after the retired-layout residue check that precedes every command; it checks no addressed Run Record, ledger, runbook, blocker, or confirmation phrase and writes nothing, so `rtm spawn rev --run run-001 --run run-002 --bind ticket=t-7` spawns nothing.

## Worktree Scope

Implement only [the accepted repeated run refusal issue](../issue/i-069-repeated-run-refusal/spec.md).
Existing source boundaries: `src/cli.rs`, where the `--run` arms of `fn hold`, `fn resume`, `fn recover`, `fn spawn`, and `fn respawn` gain the repeat check inside their existing argument loops, and the public suites `test/qa/tests/t117_descriptive_run_roster.rs` and `test/qa/tests/t120_residue_refusal_precedence.rs`. `fn status`, `fn step`, `fn intent`, and `fn abandon` do not change. The five may check in place or share one small helper, as long as each keeps its own roster shape; routing them through the shared addressing parser would add its `next:` line, which their roster shape excludes. Add only the directly required module or command wiring where the accepted design calls for it; keep unrelated behavior unchanged.
