# Ticket: t-139 — lane builds stay private

## Vertical Outcome

Every private lane test that runs Cargo on the repository or on another lane's crate - to build and launch an Engine (`rtm`, `rtm-qa`) or another binary of this repository (`edition-cut`, `snapshot-manifest`), or to run that crate's tests - builds in an output folder only that lane uses: a folder named after the lane inside the lane's own build output, handed out by one locked-folder helper in the baseline support. The first call in a run takes an exclusive lock on that folder's `lane.lock` and holds it until the run's process ends, so a second run of the same lane waits and says so in one line naming the lock file. Every `cargo build` and `cargo test` the lane runs takes that folder as its output folder, and every binary it launches is the one that build reported, found through the shared function `built_executable` from the ticket for test Engine from build messages (`t-137`). No lane reads, runs, or rebuilds the repository's shared build output: with that output rewritten, or replaced by a plain file, and the lane started twice at once, each run gives the lane's standalone verdict. Every lane keeps its identity, requirement, and assertion strength, and the single-Engine-binary lane (`t-086`) still proves, inside its own folder, that building the shipped command leaves the test Engine untouched. Per-test scratch folders, a hold barrier shared between cases, wall-clock limits, and public suites, except as concurrent writers, stay out of scope; if verdicts still differ once no lane shares build output, wall-clock limits are the next suspect and the wish stays open.
