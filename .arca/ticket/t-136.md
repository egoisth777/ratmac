# Ticket: t-136 - Lock waits survive a peer's release and a busy policy step

## Vertical Outcome

Engine invocations that compete for a lock wait their turn and then proceed. They never refuse
because a peer was in the middle of letting go, or because a short write sat behind slow Git work.
Two live regressions on `main` (`44c1dc4`), both triaged as **live regression** under
[RLR-001](../schema.md#rlr-001---triage-precedes-the-act), are fixed under their own gap records.
The lanes that caught them keep their assertions exactly as written:

1. **[ENS-005](../goal/spec.md#integrated-engine-namespace-requirements) - [res-110](../residual/res-110.md).**
   On Windows, a lock holder releases by marking its pathname for deletion and then closing its
   handle. Until the close, every open of that pathname fails with `Access is denied. (os error 5)`.
   The under-root single try and the ignore-policy claim already read that window as "someone else
   holds it". The two waiting domains, the root lock and the Run lock, read it as a filesystem
   refusal and stop at once with `cannot open lock <path>: Access is denied. (os error 5)`.
   `test/qa/tests/t036_rat007.rs::lock_and_compatibility_policy` (two concurrent `rtm step` on one
   Run) failed this way in t-135's proof 3. The lock and step source is byte-identical on `main`.
   80 isolated runs of that suite on `44c1dc4` did not reproduce it, because the window is very
   short. So the focused check forces it with a seam instead of hoping for a race.
2. **[WEB-002](../goal/spec.md#integrated-wishlist-fulfillment-requirements) - [res-176](../residual/res-176.md).**
   The ignore-policy step takes its Engine-root claim before any work and holds it through four Git
   processes: the work-tree check, the indexed-runtime listing, and two effective-rule queries. So
   N concurrent steps queue for about N times one step's Git time against the fixed five-second
   wait. Eight concurrent `rtm init` take 4.7-5.5 s on this host, and the last waiter refuses
   `cannot serialize the policy step: lock wait expired`.
   `test/qa/tests/t121_engine_ignore_initialization.rs::webv_008` failed 4 of 5 runs on a clean
   build of `main`, and in t-135's proofs 2 and 4.

The wait bound itself is not the defect and does not move: one monotonic deadline per wait, five
seconds, retry every ten milliseconds ([res-110](../residual/res-110.md)'s killed mutant
"resetting the pair deadline each retry" stays killed).

## Observable Output

**Release window is contention (ENS-005).**

- Every waiting acquirer of the root lock or a Run lock treats the release window as contention:
  `rtm start`, `rtm step`, `rtm hold`, `rtm abandon`, `rtm spawn`, `rtm respawn`, `rtm recover`,
  and every other caller of `RootLock::acquire`, `RunLock::acquire`, or `acquire_root_then_run`.
  The release window is defined as: on Windows, an open of the lock pathname fails with
  `ERROR_ACCESS_DENIED` while the pathname names a non-directory entry or has just vanished. This
  covers the claiming open and the availability probe used while waiting, and the attribute read
  each of them takes of the lock pathname just before its open. The acquirer retries
  inside its one existing deadline and claims normally once the peer's handle closes. The outcome
  is today's outcome for an ordinary contended wait.
- A directory at a lock pathname still refuses at once with today's text,
  `cannot open lock <path>: <error>` (HT-073-05 unchanged).
- When the deadline passes while the most recent failed open was still in that window, the
  refusal is `cannot open lock <path>: <os error>`, naming the last open error, never
  `lock wait expired`. Exit code, command prefix, forward-slash path rendering, and the
  "nothing modified" guarantee are those of today's open refusal. The ignore-policy claim follows
  the same rule, inside its existing
  `refusing to install the ignore policy: cannot serialize the policy step: <error>; nothing was modified`
  wrapper.
- A live holder that outlasts the deadline still refuses `lock wait expired: <path>`, byte for
  byte as today.
- The under-root single try keeps returning "not acquired" for the window. Unix has no window,
  and its behavior is unchanged.
- Decision trace (`RATMAC_TRACE`) and operation log (`RATMAC_TEST_OPERATION_LOG`) record for a
  release-window wait exactly what they record for an ordinary contended wait.

**The policy claim covers only the policy bytes (WEB-002).**

- Git inspection that does not read the policy bytes runs before the claim is taken. That is the
  inside-a-work-tree check and the indexed-runtime refusal. Their refusal texts are unchanged. When
  an indexed runtime file and a busy claim coincide, the indexed-runtime refusal now comes first.
- Under the claim: read the policy file, merge the missing lines, staged write, replace. Bytes,
  line order, staged-file handling, and "nothing was modified" on refusal are unchanged.
- A caller that finds all four lines already present writes nothing. It releases the claim
  before its effective-rule verification, which then runs unserialized.
- A caller that writes keeps the claim through its own verification and, if verification
  refuses, through restoring the prior bytes. No concurrent caller can therefore report success
  on lines a refused writer later removes.
- Consequence: a waiter waits for at most one writer's step, never for the number of concurrent
  callers. Sixteen concurrent `rtm init` on a fresh repository all exit `0`. Afterwards the
  policy file holds the operator's bytes followed by each of the four lines exactly once. Each
  caller prints today's stdout for what it did.
- A successful `rtm init` still records `lock` then `target` in the operation log (WEBV-014).
  `rtm start` and the endpoint's child initialization use the same step and gain the same bound.
  `rtm start`'s admission rollback is unchanged.

**Test-only seams.** Compiled only with feature `test-fault-injection`; production builds contain
neither.

- `RATMAC_TEST_LOCK_HOLD=unlink`, with the existing `RATMAC_TEST_LOCK_MARKER`,
  `RATMAC_TEST_LOCK_RELEASE`, and `RATMAC_TEST_LOCK_HOLD_TIMEOUT_MILLIS`. A root or Run lock's
  release pauses after its pathname removal has been requested and before the kernel unlock and
  handle close. On Windows the pathname is delete-pending for the whole pause. The marker reads
  `holding unlink lock <path>` plus LF, the existing hold's format. As with `release`, only the
  durable domains honor it, and the policy claim stays silent. A Run claim that stays silent in
  the trace - the fresh mint's claim on its new Run lock, and the endpoint's own Run claims - skips
  it, so in `rtm start` the root lock is the first release that pauses. The `release` hold is
  unchanged and still fires for those claims.
- `RATMAC_TEST_POLICY_PAUSE=<boundary>`, with `RATMAC_TEST_POLICY_PAUSE_MARKER`,
  `RATMAC_TEST_POLICY_PAUSE_RELEASE`, and `RATMAC_TEST_POLICY_PAUSE_TIMEOUT_MILLIS`. It mirrors
  `RATMAC_TEST_RECOVER_PAUSE` in every rule:
  - marker content is the boundary name plus LF;
  - release happens when the release file exists;
  - the default timeout is 60000 ms;
  - companions are checked before any claim or write;
  - unset, empty, or unrecognized values are inert.

  Boundary `inspect` pauses inside the pre-claim Git inspection. Boundary `verify` pauses at the
  start of effective-rule verification, holding the claim only for a caller that wrote. Expiry
  refuses through the step's ordinary refusal path as `injected policy pause at <boundary> expired`,
  leaving every byte as found.

**Regression adjustment this contract requires.** Cutting this ticket reopened the root and Run
lock gap record (`res-110`). The schema's reopen rule moved it from `.arca/residual/archive/`
back to the active folder, and once it is satisfied again it may return to the archive with new
bytes. The shared private test support history check (`WCPV-006` in
`test/qa/tests/t126_shared_private_test_support.rs`, under
[WCP-002](../schema.md#wcp-002--shared-private-test-support)) reads every archived gap record in
its frozen inventory and requires the frozen bytes at the archive path, so it refuses this
authorized move today, on `main` as in this worktree: `preserved artifact
.arca/residual/archive/res-110.md: The system cannot find the file specified. (os error 2)`.
History checks accept every authorized move, as the archive-aware oracle does for issues
([AOI-002](../goal/spec.md#integrated-acceptance-oracle-integrity-requirements),
[accepted mechanics](../goal/design.md#reviewable-snapshots-and-honest-acceptance-oracles-aoi-001aoi-003)).
So that one check changes: an archived gap record that is absent from its archive path, or no
longer matches its frozen bytes, passes only when

- a line appended to `.arca/log.md` after the inventory's frozen prefix names that record and a
  reopen; and
- exactly one copy of the record exists, at its archive path or under the same name in the active
  folder, and that copy's first `residual-id` line still names it.

An archived record still byte-identical to its frozen bytes passes as before. Every other
difference still fails: a record changed or removed with no such line, a reopen line found only in
the frozen prefix, a record left in both folders or in neither, a copy whose id changed, and a
reopen line that names a different record. The rule matches the word anywhere on the line, so a
line that names a record and says it needs no reopen counts too; a human reads every appended log
line. Nothing else in that file changes, and both frozen inventories stay byte-identical.

- **Known adjacent risk, not fixed here:** `rtm start` rolls its policy bytes back after the
  step released its claim. A concurrent `rtm init` that found those lines present can report
  success before that rollback removes them. This predates this ticket (t-121) and is left for a
  wish.
- **Known adjacent risk, not fixed here:** `rtm abandon` checks whether the root and Run lock
  pathnames exist while it plans, before it takes any lock (`src/abandon.rs`,
  `lock_path_present`). That attribute read can meet a peer's release window the same way and
  refuse `abandon cannot inspect lock <path>: <os error>`. It is not a waiting acquirer, its
  text is not named above, and it is left for a wish.
- **Cross-Feature:** a linked worktree and the primary checkout share one Engine root, and both
  run the same step with different authoring probes.
