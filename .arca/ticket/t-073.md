# Ticket: t-073 — Lock split

## Vertical Outcome

The repository root lock is held only for identity and shared-roster or ledger mutation.
Motion of an existing Run uses that Run's own lock, so different Runs can move concurrently;
when both locks are needed they are acquired root-before-Run, and a potentially long guard
runs after the root lock is released.

## Worktree Scope

- **Included:** root-lock and per-Run-lock path and guard types; ordered acquisition around
  minting, roster, and ledger mutation; motion serialization for one addressed Run; release
  before guard evaluation; rollback/release behavior on refusal and error; QA coverage in
  `test/qa/tests/t073_lock_split.rs`; and six private lane checks.
- **Excluded:** Engine-root resolution and durable identity foundations (`t-071` and
  `t-072`); new workspace binding (`t-074`); changes to the meaning of guards, Run
  addressing, or ledger records. This ticket does not introduce a global lock held across
  unrelated Run motion.
- **Expected merge/output:** two different Runs can make progress while two operations on
  one Run serialize, shared mutations remain protected by the root lock, and a blocked or
  long-running guard cannot prevent an independent root-lock operation merely by waiting.
- **Superseded-test fate:** the single `.arca/rtm.lock` arbitration expectation is replaced
  by root and Run lock assertions; existing same-Run consistency checks remain authoritative.
  Ownership now rests on a kernel claim held on the holder's open handle, so a leftover lock
  file with no live holder behind it stops blocking anything: in
  `test/qa/tests/t051_abandon.rs::stale_lock_retired_not_bypassed` the seeded token bytes no
  longer refuse a mint or a motion, and a confirmed abandon is no longer the only way to clear
  the residue. That test keeps its two surviving intents verbatim - no bypass flag exists, and
  leftover lock files never wedge a fresh invocation - and now proves the second directly
  rather than through a retirement dance. `lock::root_path` and `lock::run_path` stay public
  because `t022_r026`, `t023_r015`, `t041_guard_diagnostics`, and `t051_abandon` address locks
  by path. `ENSV-006` changes fixture with the same reasoning: its foreign root lock is now
  held by a live `lock_barrier` process holding a real claim instead of written token bytes,
  and the test additionally asserts that an unheld leftover root lock file blocks no mint.

## Inherited findings (2026-08-06, from the t-072 independent review)

Two defects were proven while reviewing `t-072` and are out of that ticket's scope. They are
this ticket's work and must be closed by its landing:

- The root lock is held while a guard runs an external command: `Scheduler::step` acquires the
  root lock, then calls `guard_failures`, and a command guard waits for a child process. That
  is the ENS-005 violation `ENSV-006` and `HT-073-06` already target, now with a proven
  callsite rather than a hypothesis.
- `abandon` schedules any extant `root.lock` for retirement and removes it without acquiring
  or owning it, while the original guard later removes the same pathname when it drops. Until
  that is fixed, "the caller holds the root lock" is a pathname convention, not exclusivity, so
  `t-072`'s mint precondition rests on this ticket. `HT-073-04` must cover a retired-lock race
  that would otherwise let two callers mint at once.


## P5 notes (2026-08-06)

- **Change.** `src/lock.rs` owns both lock kinds and nothing else: `root_path` is
  `<engine-root>/locks/root.lock`, `run_path` is `<engine-root>/locks/runs/<id>.lock`, and
  ownership is a kernel claim held on the holder's open handle - `flock` on Unix, a
  `LockFileEx` byte-range claim on Windows. `acquire_root_then_run` takes root, tries the Run
  once, releases root before any wait, waits on the Run without holding root, and re-enters,
  all inside one monotonic deadline that no retry resets. `Scheduler::step` takes only the
  addressed Run lock on every path, so a long guard blocks nothing but its own Run.
- **Root's domain.** Minting, roster and ledger mutation, and shared ticket mutation. The
  ticket joined the list because a read-modify-write of a file shared across Runs cannot be
  serialized by a per-Run lock: two holds naming one ticket from different Runs each compared
  and replaced it, and both reported success. Shared history is not in the list - appends are
  single append-only writes that commute, so `step` and `apply_hold` take no root lock to
  record themselves, and nothing rewrites or truncates `.ratmac/log.md`. A transaction that
  already appended and then fails compensates with a further append.
- **The token is diagnostic.** No decision reads it. Ownership is the kernel claim plus a
  device-and-inode identity check against the guard's own open handle, at the mutation
  boundary and again on release; the release unlinks while still claimed and then unlocks.
  The superseded token-and-process-id design left `a76bf96` entirely.
- **Honest failures.** A refusal names what actually happened: an unopenable lock path is
  `cannot open lock <path>` with the original error, never a wait that expires; on Windows a
  weak read open plus a shared range claim distinguishes a live exclusive holder from an ACL
  that denies write or delete, with one retry to catch a holder that left in between. A failed
  ledger append is classified by re-reading the ledger - complete means committed and nothing
  rolls back, absent permits rollback, partial or unreadable destroys nothing and reports both
  paths. Every rollback site compares the bytes it wrote before deleting anything, and cleanup
  or rollback failures are reported rather than swallowed.
- **Documented limit.** On Unix the window between the identity check and the pathname unlink
  cannot be closed with the portable API, because POSIX unlinks a pathname and not an inode.
  `src/lock.rs` says so where the check lives. It is reachable only by a local actor with write
  access to `.ratmac/locks/` who deliberately replaces a lock path - outside the cooperative
  threat model, and an actor who can do that can delete the Run outright.
- **Private lanes.** All six in `.arca-private/t-073` are green, and their strength was
  measured rather than assumed. A mutation battery against the earlier tree left six mutants
  alive; five now die with a red and a green either side - removing the kernel claim, unlocking
  immediately after claiming, resetting the pair deadline each retry, deleting the `apply_hold`
  stale-plan comparison, and unlinking after unlocking. Two later fixes were proved the same
  way: deleting the Join-ledger revalidation let a stale verdict commit, and releasing root
  early around the shared ticket write failed the root-held assertion. `HT-073-02` and
  `HT-073-03`'s original halves remain honest regression guards carrying no acceptance weight.
- **Unexercised.** The post-claim pathname-identity revalidation cannot be shown red on this
  host: Windows refuses external rename or delete while the live no-delete-share handle exists,
  so removing the check changes nothing observable. Its value is on Unix and it needs a Unix
  runner. Recorded in the `HT-073-01` row rather than covered by a substitute mutation.
- **Independent review.** `t073-recheck` rejected three successive trees before approving this
  one. Its findings, all landed: Git subprocesses still ran inside root scopes, so the hoist was
  incomplete; rollback in spawn and respawn could erase a concurrent winner; addressed abandon
  chose Run-only whenever no root pathname happened to exist; roster reads collapsed I/O errors
  into an empty roster; hold could leave a truncated ticket and overwrite an out-of-band edit;
  a Join verdict could commit against a ledger that changed after evaluation; and two holds on
  one ticket from different Runs did not serialize. The final verdict is APPROVE.
- **Reviewable snapshot.** Cited by `res-110`, not here: that record names the manifest path,
  its row count, and its one declared exception.
