# Ticket: t-073 — Lock split

## Vertical Outcome

The repository root lock is held only for identity and shared-roster or ledger mutation.
Motion of an existing Run uses that Run's own lock, so different Runs can move concurrently;
when both locks are needed they are acquired root-before-Run, and a potentially long guard
runs after the root lock is released.

## Worktree Scope

- **Included:** root-lock and per-Run-lock path and guard types; ordered acquisition around
  minting, roster, and ledger mutation; motion serialization for one addressed Run; release
  before guard evaluation; rollback/release behavior on refusal and error; QA coverage in
  `test/qa/tests/t073_lock_split.rs`; and six private lane checks.
- **Excluded:** Engine-root resolution and durable identity foundations (`t-071` and
  `t-072`); new workspace binding (`t-074`); changes to the meaning of guards, Run
  addressing, or ledger records. This ticket does not introduce a global lock held across
  unrelated Run motion.
- **Expected merge/output:** two different Runs can make progress while two operations on
  one Run serialize, shared mutations remain protected by the root lock, and a blocked or
  long-running guard cannot prevent an independent root-lock operation merely by waiting.
- **Superseded-test fate:** the single `.arca/rtm.lock` arbitration expectation is replaced
  by root and Run lock assertions; existing same-Run consistency checks remain authoritative.

## Inherited findings (2026-08-06, from the t-072 independent review)

Two defects were proven while reviewing `t-072` and are out of that ticket's scope. They are
this ticket's work and must be closed by its landing:

- The root lock is held while a guard runs an external command: `Scheduler::step` acquires the
  root lock, then calls `guard_failures`, and a command guard waits for a child process. That
  is the ENS-005 violation `ENSV-006` and `HT-073-06` already target, now with a proven
  callsite rather than a hypothesis.
- `abandon` schedules any extant `root.lock` for retirement and removes it without acquiring
  or owning it, while the original guard later removes the same pathname when it drops. Until
  that is fixed, "the caller holds the root lock" is a pathname convention, not exclusivity, so
  `t-072`'s mint precondition rests on this ticket. `HT-073-04` must cover a retired-lock race
  that would otherwise let two callers mint at once.
