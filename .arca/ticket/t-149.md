# Ticket: t-149 — abandon release window

## Vertical Outcome

While holding no lock, `rtm abandon` checks whether the project's root lock and the addressed Run's lock exist. When that check meets another command's release of one of those locks and, on Windows, the read answers `Access is denied. (os error 5)`, abandon reads again within the lock module's five-second wait bound, measured from the first denial, and acts on the settled answer, present or absent, exactly as without the release; settled means the first read after the window that succeeds or answers not-found. Only a read failure that outlasts the bound, or any other read error, refuses with today's text `abandon cannot inspect lock <path>: <error>`, carrying the last error, inside today's message for that route (on the planning route, `rtm: abandon refused; abandon cannot inspect lock <path>: <error>`), exit code 1. The wait holds no lock, so no other command waits on abandon, and other platforms keep the single read.

## Worktree Scope

Implement only [the accepted abandon release window issue](../issue/i-072-abandon-release-window/spec.md).
Existing source boundaries: `src/abandon.rs`, whose `fn lock_path_present` keeps its attribute read and returns the settled answer, and `src/lock.rs`, which gains the settled read as one crate-visible helper, as the accepted mechanics give it, so the release-window classifier (`fn transient_release_window`), the retry interval, and the bound stay in one place; `fn run_lock_is_contended` keeps its own deadline, and the apply step's lock acquisitions stay as they are. The checks use one test-only fault, compiled only with the `test-fault-injection` feature like `fn inject_lock_fault`, whose spelling the issue left to this ticket. Its selector, `RATMAC_TEST_LOCK_PRESENCE_FAULT`, names which lock's presence reads fail (`root`, `run`, or both, the domain words the existing lock fault `RATMAC_TEST_LOCK_FAULT` uses), how many reads fail or every read, and the raw error code (5 for the release-window cases, 32 for the other-code control). Its companion, `RATMAC_TEST_LOCK_PRESENCE_RECORD`, names the file outside the project where each injected failure is recorded. Both are `RATMAC_TEST_*` settings, so the case-scoped hook rule (`SVE-006`) covers them, and the classification, the wait, and the settled read run unchanged under the fault. Add only the directly required module or command wiring where the accepted design calls for it; keep unrelated behavior unchanged.
