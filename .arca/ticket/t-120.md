# Ticket: t-120 — residue refusal precedence

## Vertical Outcome

For every public operational command and equivalent library entry point, retired-layout residue at the invoking/shared or explicitly addressed project is refused before command-specific option validation, runbook parsing, roster reads, blocker lookup, target existence checks, joins involving runtime data, or mutation. Only the minimal command/target identification, Engine-root resolution, and filesystem inspection required to locate residue may precede that refusal. Thus a recognized command with malformed options reports residue first when residue exists; without residue it reports the ordinary option error. Only documented exact standalone-help forms and an unknown command perform no operational action and remain pure usage responses. All refusals leave the tree byte-identical. A help token mixed into an operational request cannot bypass preflight. A single maintained entry-point matrix covers every public route, including new initialization, recovery, authorization, and nested-protocol commands, and exposes a newly added uncovered operational route.

## Observable Output

Defined before implementation. The public checks and the private lanes both judge this shape; neither needs the other's arrangement or the source.

**Retired-layout residue** is exactly what the Engine's existing residue check finds, in its existing order and with its existing refusal texts; this ticket adds and drops no shape:

- a flat Run artifact `<Engine root>/state.toml`;
- a pre-split artifact `.arca/ratmac.toml`, `.arca/runs`, `.arca/rtm.lock`, or `.arca/state.toml` in the inspected checkout or in the primary checkout that holds its Engine root - any object type, a dangling link included; `.arca/` alone and `.arca/evidence/` are not residue;
- a pre-cutover runbook: the inspected checkout's `.ratmac/ratmac.toml` declaring a top-level `phases` table or a `classes.<name>.phases` table (`RB111`);
- a pre-cutover Run Record under `<Engine root>/runs/<id>/`: a `state.toml`, or a `run.toml` with a line whose text after leading whitespace starts `phase =`.

Each refusal text names the artifact with forward slashes and its repair, and ends `nothing was modified`. The legacy lock `.ratmac/schd.lock` (RAT-007) is a legacy-identity artifact, not retired-layout residue: its check, its text, and its place are unchanged.

**Preflight order.** A recognized command, before anything else it does, inspects (1) the invoking checkout with its Engine root, the shared primary checkout included - every command - then (2) the project its arguments explicitly address, when the target scan below identifies one. The first residue found refuses. Before that refusal only three things may happen: splitting the arguments into command and target, Engine-root resolution (each project at most once, the t-119 rule), and the residue inspection. None of these may come first: option validation of any kind (unknown, repeated, missing, or valueless options; `--run` syntax; `--bind` shape; confirmation phrases; extra positionals), runbook parsing, roster reads, Run Record or spawn-ledger reads, blocker lookup, target existence checks, lock acquisition, or any write. Without residue every route answers exactly as before - output, argument errors, their texts, and exit codes - except for the help rule below.

**Target scan.** Non-validating: it judges nothing malformed.

| Command | Explicitly addressed project |
| :--- | :--- |
| `doctor`, `scaffold`, `skill` | The first argument after the command that does not begin with `-` names the target; its project follows the existing addressed-project rule (the target's directory, or that directory's parent when it is `.ratmac/` or the legacy `.arca/`). |
| `spawn` | The `--workspace` directory, only when `--workspace` occurs exactly once and the next argument exists, is non-empty, and does not begin with `--`; a relative value joins the invoking checkout. It is judged against the invoking Engine root and is never resolved (the t-119 rule). |
| `start`, `status`, `step`, `hold`, `abandon`, `respawn` | None: they address only the invoking checkout. |

With no identified target - none given, or `--workspace` repeated or without a usable value - only the invoking checkout is inspected, then the ordinary usage error follows. A second positional, an unknown option, or `--json` given twice is a later argument defect, reported only after both inspections pass. A Run named by `--run` is located through runtime data (the roster and its parent's spawn ledger), so a child Run's bound workspace is not an explicitly addressed project: its residue check keeps its present place after the address is validated, and the invoking checkout still refuses before any of that.

**Refusal shape.** Texts are the existing ones; stdout is empty; the tree stays byte-identical.

| Residue in | Binary stderr (`cli::run_from`: the error's text is what follows `rtm: `) | Exit |
| :--- | :--- | :--- |
| the invoking checkout or its shared root | `rtm: <command>: <refusal>`; `status` keeps its trailing `next:` line | 1 |
| `doctor`'s addressed project | `rtm: <refusal>` | 2 |
| `scaffold`'s or `skill`'s addressed project | `rtm: <refusal>` | 2 |
| `spawn`'s `--workspace` | `rtm: spawn: <refusal>` | 1 |

**Help and unknown commands.** Tokens are the arguments after one optional leading `rtm`.

- No tokens, or a first token that is not in the route table: nothing is resolved, inspected, read, or written. With no tokens, or with `--help` or `-h` among them, the general usage prints on stdout, exit 0 (`rtm`, `rtm --help`, `rtm -h`, `rtm bogus --help`, as before); otherwise `unsupported command or option: <first token>`, exit 1.
- A command followed by exactly one token that is `--help` or `-h`: that command's help on stdout, exit 0; nothing resolved, inspected, read, or written. These are the only pure help forms.
- A command with `--help` or `-h` among any other arguments (`rtm step --run run-001 --help`, `rtm doctor --json -h`, `rtm spawn -h --help`) is an operational request: the preflight runs and refuses on residue; without residue the command's help prints on stdout, exit 0, and nothing else runs.

**Route table.** The general usage's `Commands:` line is the one public route table; today it reads `Commands: start, status, step, hold, abandon, spawn, respawn, doctor, scaffold, skill`. A first token is a command exactly when that line lists it: every listed command reaches its own route, and any other first token (`init`, `recover`, `review`, `launch`, `receipt`, `run`, for example) is an unknown command. A verb added to dispatch is added to that line, and a public matrix that reads the line fails until it covers every listed command. No new public item is added for it.

The oracle's endpoint families map onto today's routes: initialization is `start`; recovery is `respawn` and `abandon`; review/authorization is `hold` and a confirmed `abandon`; nested launch is `spawn`; the receipt and completion endpoints (`receipt::gate_sensitivity`, `completion::gate_completion`) are guard predicates reached only through `rtm step` and take an explicit Engine root, so `step` carries their preflight.

**Library entries.** Each public path-taking entry of the t-119 table except `Scheduler::runs_dir` (which reads and writes nothing) inspects its project before any other read - the given root; for `doctor::diagnose`, `scaffold::write_scaffold`, and `skill::write_skill` the path's project; for `Scheduler::spawn_to_with_workspace` also a given workspace - and on residue returns its refusal with nothing else read or written. Invalid request values (an unknown or empty run id, a wrong confirmation, a missing blocker, an occupied path, an undeclared spawn name, unknown bindings) never win over residue.

| Entry | Refusal on residue |
| :--- | :--- |
| `cli::run_from` | what the same command line answers |
| `Scheduler::{open, open_run, run_roster, spawn_to, spawn_to_with_workspace, respawn}` | `Err(StateError)` whose text is the refusal |
| `abandon::{resolve_target, plan_abandon, apply_abandon}`, `blocked::{plan_hold, apply_hold}` | the entry's `Err` refusal, whose text contains the refusal |
| `doctor::diagnose` | exactly one error finding: code `RB111` for a pre-cutover runbook, otherwise `RB101`; its message contains the refusal |
| `scaffold::write_scaffold`, `skill::write_skill` | `Err(Preflight(<refusal>))` |
| `contract::{gate_intake, work_items, gate_records}` - new | `Err` holding exactly one `ContractDefect`: `artifact` the project's checkout path with forward slashes, `reason` the refusal |
| `contract::unproven_mechanization` - new | exactly that one defect |
| `machine::MachineClass::load_from_project_root` - new | `Err(MachineClassParseError)`: code `RB111` for a pre-cutover runbook, otherwise `RB101`; location the checkout's `.ratmac/ratmac.toml` with forward slashes; message the refusal |

Rows not marked new already hold and must keep holding. Methods called on an already opened `Scheduler` keep their existing recheck. Lower-level public items that take an Engine root, Run directory, ledger, or artifact path rather than a project (`lock`, `ledger`, `mint`, `receipt`, `completion`, `channel`, `pin`, `goal`, and the `*_at` contract gates) are building blocks, not command-equivalent entries, and are unchanged.

**Operation observer.** Builds with the `test-fault-injection` feature read `RATMAC_TEST_OPERATION_LOG=<file>` at each operation boundary below and append one line, the kind then `\n`, creating the file when absent. Unset or empty, or a build without the feature: nothing extra is read or written.

| Kind | Boundary |
| :--- | :--- |
| `roster` | a read of `<Engine root>/runs/` that lists, counts, or validates Run ids: roster summaries and rows, `--run` validation, next-act hints |
| `record` | reading a Run's Run Record or evidence |
| `ledger` | reading a spawn ledger |
| `runbook` | parsing a runbook into a Machine Class |
| `blocker` | looking up a hold's blocker reference |
| `target` | checking whether a command's target exists: a scaffold or skill path and its parent, a skill's partial folder, a spawn workspace |
| `lock` | acquiring the root lock or a Run lock |

The residue inspection logs nothing: its existence checks, its runbook byte scan and `phases` parse, and its listing of `runs/` for pre-cutover records are not operations. So a refusal for residue in the invoking checkout, its shared root, or an addressed project leaves the file absent; so do the pure help forms and unknown commands. Writes are judged by byte snapshots; every mutating route logs `lock` or `target` before it writes. Clean positive controls, each logging at least these kinds: `rtm start` - `runbook`, `lock`; `rtm status --run <planned Run>` - `roster`, `record`, `runbook`; a valid `rtm hold` - `blocker`, `lock`; a legal `rtm spawn <name> --run <parent>` - `ledger`, `lock`; `rtm scaffold <new path>` and `rtm skill <new path>` - `target`; `rtm doctor` - `runbook`.

**Root counts (t-119).** One row changes: `rtm doctor [--json] <runbook>` resolves the invoking checkout and the runbook's project, each once - one line when they are the same directory. A command line with a help token among other arguments resolves what its preflight inspects, each once. Every other row holds as landed; pure help forms and unknown commands resolve nothing.

**Confirmed retirement.** `rtm abandon` and the abandon entries may still recover a Run whose runbook pin drifted (unchanged), but residue in the invoking checkout refuses first, even with the correct confirmation, and nothing is retired, moved, or repaired.
