# Ticket: t-127 — edition proof preflight

## Vertical Outcome

The supported edition-cut path validates the candidate annotation using the same proof-text contract as the edition audit, confirms the exact intended clean commit and all required successful checks against its bytes, validates edition naming/sequence and target reachability, and proves the edition rule EDN-001 rest condition at that commit before creating a tag: no pending intake, no open work item, and no unproven gap record. A missing proof phrase, failed or stale check, unfinished cycle despite green quality commands, dirty tree, moved target, existing name, or malformed input creates no tag and alters no existing tag. A valid cut creates one immutable annotated tag using the validated text and exact checked commit; ledger recording still follows tag creation. Text that merely names checks is not proof that they passed.

## Observable Output

Defined before implementation. The public checks and the private lanes both
judge this shape; neither needs the other's arrangement or the source. Every
sentence below is observable through the process exit code, stdout/stderr
bytes, the git refs and tag objects of the addressed repository, or the
working-tree bytes of files the operation reads. `edition-cut` is a harness
contributor tool, not an Engine command: it takes no locks, touches no
`.ratmac/` Engine root, writes no operation log, and its only operational
write is the one tag creation described below - besides the pause marker
the armed test seam names, which is the test's own file. Paths in messages
keep the spelling the caller supplied; repository-relative record paths
below use forward slashes.

**Terms.** The *candidate* is the proposed edition name, message bytes,
target revision, and declared checks supplied on the command line. The
*resolved commit* is the full 40-hex hash `git rev-parse --verify
--quiet <rev>^{commit}` returns, taken once. The *declared checks* are the
command lines of the checks file, one check per line, each split on
whitespace into one program and its arguments - never a shell. The *proof
text* is the message file's bytes; the *proof-text contract* is
[`RECORDED_BAR`](../../test/qa/src/edition.rs) (test/qa/src/edition.rs:22-29),
the six phrases an edition's message must carry. The *rest records* are the
candidate commit's `.arca/issue/`, `.arca/ticket/`, and `.arca/residual/`
trees. *Preflight* is every check that must pass before the tag-creation
step begins; `--check-only` runs the whole preflight and creates nothing.
`<highest>`, `<expected>`, and `<NNN>` in the texts below render as
three-digit zero-padded numbers, matching the audit's `{:03}` formatting.

**The carrier and the one validator.** A new harness binary `edition-cut`
(`test/qa/src/bin/edition_cut.rs`, wired as a `[[bin]]` in `test/qa/Cargo.toml`
beside `guard-probe`, `snapshot-manifest`, and `lock-barrier`). The
proof-text rule becomes one pure public function in the shared oracle
module - `edition::missing_phrases(message: &str) -> Vec<&'static str>`,
returning the `RECORDED_BAR` entries `message` lacks, in `RECORDED_BAR`
order - and both `audit_editions` (its `documented` finding,
test/qa/src/edition.rs:131-141) and the preflight call exactly that
function; for the same message bytes, the stage-2 refusal and the audit's
`documented` finding name the same missing phrases in `RECORDED_BAR` order.
Every other public item of `test/qa/src/edition.rs` keeps its name,
signature, and
output bytes: `audit_editions`, `audit_sequence`, `read_ledger`,
`edition_tags`, `edition_commit`, `edition_number`, `trunk_name`, `git`,
`report`, `repo_root`, `EDITION_PREFIX`, `RECORDED_BAR`,
`EXAMPLE_BAR_MESSAGE`, `LEDGER_PATH`, `AuditFinding`, `LedgerRow`.

**Command surface.** Exactly:

```
edition-cut --repo <path> --name <edition-NNN> --message-file <path> --checks <path> [--at <rev>] [--check-only]
```

All four leading flags are required; `--at` defaults to `HEAD`;
`--check-only` defaults to off. The message travels only through
`--message-file` (bytes, no shell, no `-m` interpolation); the checks
travel only through `--checks`. There is no help form and no other flag:
any other token, any flag without its value, and any missing required flag
refuse as malformed input below, before any git command runs.

**Stage order.** Preflight runs in this fixed order and refuses at the
first failing stage; no later stage's read happens. No stage writes
anything.

0. **Seam arguments.** Validate the pause-seam variables of the test-only
   section below, before any git command.
1. **Own inputs.** Required flags present and valued; `--name` is exactly
   `edition-NNN` with three digits (the shape `edition_number` accepts,
   test/qa/src/edition.rs:240-246); the message file is readable UTF-8; the
   checks file is readable UTF-8 holding at least one check, every line one
   program and its arguments (no blank line, no leading whitespace).
   Within this stage the checks run in the order written here, so an
   invocation with several bad inputs refuses naming the first.
2. **Proof text.** The message passes the same validator the audit uses: a
   message whose bytes are empty after trimming refuses with the audit's
   empty-message words; a message missing phrases refuses naming exactly
   the missing ones in `RECORDED_BAR` order. A message that does not end
   with exactly one LF, or ends with a blank line (one holding nothing or
   only spaces and tabs), refuses here: the
   candidate must be a normalized annotated-tag message. Storage fidelity
   is pinned by the verbatim creation of stage 10, not by git's default
   cleanup.
3. **Resolve once.** `--at` resolves to the resolved commit. An
   unresolvable or ambiguous revision refuses carrying the shared
   `edition::git` error text (test/qa/src/edition.rs:54-71).
4. **Clean proven checkout.** `HEAD` is exactly the resolved commit, and
   `git status --porcelain` output is empty - no staged, unstaged, or
   untracked entry (ignored paths excluded by git itself).
5. **Existing naming health.** No existing tag matching the resembling
   patterns `edition*`/`Edition*` is malformed; the well-formed existing
   numbers run 001..highest with no hole. The audit's own finding words
   name any offender.
6. **Candidate number and name.** The candidate name does not already
   exist, and its number is exactly highest+1 (001 when no edition exists).
7. **Reachability.** The resolved commit is an ancestor of the trunk
   `trunk_name` returns (`main`; a repository without one refuses with
   today's trunk words).
8. **Rest at the commit.** The rest records read from the candidate
   commit's tree - not the working tree - satisfy EDN-001's rest condition:
   no pending intake, no open work item, no unproven gap record, per the
   scan rules below.
9. **Declared checks.** Each declared check runs in file order with the
   repository root as working directory, through the harness's scrubbed
   child environment (inherited `GIT_*` variables removed, stdin null);
   its stdout/stderr are captured and discarded, so the tool's own stdout
   stays exact. Every check must exit 0.
10. **Recheck, then create.** Immediately before the write, stages 4, 6
    (name absence), and 8 are re-run; their refusals are byte-identical to
    their preflight forms. Then the tag is created with a non-overwriting
    creation - one `git tag` command, no force - carrying
    `--cleanup=verbatim`, the validated message bytes on its stdin
    (`-F -`), and the resolved commit explicitly, never a moving name like
    `HEAD`. The verbatim cleanup pins what git stores: exactly the
    validated bytes, no `#`-comment stripping, no whitespace cleanup, so
    no legal candidate is stored altered. A
    creation failure (including a concurrent invocation winning the name)
    refuses carrying git's own error.
11. **Verify the created tag.** Read back: the name's object kind is
    `tag`, `edition_commit` returns the resolved commit, and the stored
    message equals the validated bytes exactly. Any disagreement refuses
    and the tag is never rewritten, moved, or deleted (EDN-003: repair is
    a human act, never a rewrite).

`--check-only` runs stages 0 through 9 and stops: stage 10 never runs, so
the repository is untouched and the success line below says so.

**Success output.** Exit 0, stderr empty, stdout exactly one LF-terminated
line:

```
edition-cut: cut edition-007 at 0123456789abcdef0123456789abcdef01234567; the ledger row follows in the recording landing (ELR-001)
```

(`<edition-NNN>` and the full hash vary; the rest is fixed bytes.) With
`--check-only` the line is:

```
edition-cut: preflight green for edition-007 at 0123456789abcdef0123456789abcdef01234567; --check-only, nothing was created
```

A successful cut changes exactly one thing: one new annotated tag ref
`refs/tags/<name>` whose object is a tag pointing at the resolved commit.
No other ref moves, no existing annotation changes, and the tool itself
writes no working-tree file; the declared checks' own writes are the
checks' business. The judged after-state is refs plus an empty
`git status --porcelain`, and green-path fixtures declare checks that
write nothing.

**Failure boundaries.** Every refusal: exit 1, stdout empty, stderr
exactly one LF-terminated line of the form
`edition-cut: refused; <text>`. The table gives `<text>`. `<path>`,
`<rev>`, `<arg>` keep the caller's spelling; `<hash>` is a full 40-hex
hash; `{}`-free texts are fixed bytes. In the rest rows `<file>` is the
record's repository-relative path with forward slashes (for example
`.arca/ticket/t-900.md`, `.arca/residual/res-900.md`) and `<issue-id>` is
the pending bundle's folder name under `.arca/issue/` (for example
`i-900-pending`). In the check rows `<n>` is the 1-based line number and
`<program and arguments>` is the check's whitespace-split pieces joined
by single spaces. A relative `--repo`, `--message-file`, or `--checks`
spelling is opened as spelled, against the invoking process's working
directory. Checks-file lines split at LF, and a final LF ends the last
line rather than starting an empty one: a zero-byte file declares no
check, and any empty line - a lone LF included - is a malformed line.

**Rest records - what "at rest" reads.** All three scans read the
candidate commit's tree (`git ls-tree` of the resolved commit), never the
working tree; under stage 4's identity requirement the two agree, and the
commit-side read is what EDN-001 states. Scan order is intake, then work
items, then gap records; within a category, entries sort by name and the
first offender refuses.

- *Pending intake*: any direct child directory of `.arca/issue` other than
  `deferred` and `archive` - the intake work area is exactly that location
  (schema.md, "The issue folder"); a deferred bundle does not block.
- *Open work item*: any `.md` file directly under `.arca/ticket` whose
  leading front-matter block's first `status:` line (quotes stripped) is
  not `passed`. Today's live vocabulary is `approved` (open) and `passed`
  (closed, filled at closure); a file with no readable `status:` line
  counts as open.
- *Unproven gap record*: any `.md` file directly under `.arca/residual`
  whose status is not `satisfied` - `missing` and `partial` are the
  unproven values the working rules already name. A gap record carries
  its fields in a fenced block, not in front matter: every record under
  `.arca/residual/` is `# Residual Record`, a blank line, then a block
  opened by the line `` ```yaml `` and closed by the line `` ``` ``. Its
  status is the first `status:` line inside the first such block
  (quotes stripped); a record with no such line is `unreadable`.
  Nothing here edits or creates residual records; the tool only reads.

**Checks - freshness is execution.** The tool never trusts recorded
receipts, marker files, or the message's own claims: "Text that merely
names checks is not proof that they passed" (WCP-008). A stale proof is
therefore observable as a failed execution - a fixture check that passed
at a parent commit but not at the candidate refuses at stage 9 with the
check-failed row - and a green fixture is one whose declared checks exit 0
when the tool runs them at the candidate commit. The real repository's
declaration is the EDN-001 bar (cargo test --workspace, cargo fmt
--check, cargo clippy --workspace --all-targets, tools/check_links.py,
rtm doctor); it travels as declared data in the checks file, reviewable
through `--check-only`, not as a second copy inside the tool.

**Concurrency - nothing waits.** The tool holds no locks: concurrent
invocations race only at git's own atomic ref update. Every interleaving
ends in exactly one created tag: the loser refuses at stage 6 (name seen
before its write) or stage 10 (git's non-overwriting creation fails),
and the winner's tag stands untouched. A racing writer that dirties the
tree or advances the branch between preflight and write is caught by the
stage 10 recheck; one that lands after the write cannot affect the tag,
which names the resolved commit, never `HEAD`.

**Interruption and recovery.** The operation has exactly one durable
step: the single ref write of stage 10 (git creates the tag object, then
the ref, atomically; there is no partial tag). Killing the process at any
earlier point - including inside the stage 9 checks or at the seam pause -
leaves no tag and no changed file, and a re-run starts fresh. Killing it
after the ref update but before stage 11's verification leaves a complete
tag; the re-run then refuses at stage 6 with the name-exists row, and the
WCPV-024 test witnesses the tag's bytes directly. In no interrupted state
does the tool or its re-run move, rewrite, or delete an existing tag.

**The post-cut audit boundary (what the tests assert next).** After one
successful cut, `audit_editions` on the repository returns no findings,
and `audit_sequence` returns exactly one finding for the new tag - today's
missing-ledger-row bytes: `<name>: immutable: .arca/editions.md records
nothing for it, so a move would be invisible` (test/qa/src/edition.rs:343-349).
That is the ELR-001 boundary, not a defect: the row is appended in the
next recording landing, and only that landing makes the full
`audit_sequence` pass. WCPV-024 pins the just-cut edition lacking its
ledger row until the ELR-001 recording landing, and WCP-008 assigns
preflight only naming/sequence and reachability, so full `audit_sequence`
green is not a preflight input. A repeated cut of the same name refuses
at stage 6 and leaves the tag byte-identical.

**Test-only seams.** The stage 10 recheck boundary is otherwise

  `RATMAC_TEST_EDITION_CUT_PAUSE=<value> names no boundary; after-checks

  `cannot write the pause marker <path>: <io error>`, writing nothing
