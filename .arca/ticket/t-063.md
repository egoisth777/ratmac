# Ticket: t-063 — Run completion

## Vertical Outcome

A Run ends and the Engine says so. Starting in a Phase with no ordinary outgoing edge, or stepping
into one, writes `status = "passed"` in the same atomic State File replacement that records the
position. A passed Run refuses `step` and `hold` by name without touching state. Confirmed
abandonment appends one durable `- Abandoned:` event naming the addressed Run before any active
state retires; `abandoned` never appears in a State File. Guard refusal remains byte-identical and
non-terminal; nothing writes `failed`.

## Worktree Scope

- **Included:** `src/graph.rs` ordinary-outgoing predicate, `src/scheduler.rs` start/step status
  writes plus terminal-Run step refusal, `src/blocked.rs` terminal-Run hold refusal,
  `src/abandon.rs` event literal gains the run id, `test/qa/tests/t063_run_completion.rs`,
  `.arca-private/t-063/` hidden lanes, `.arca/runbook-spec.md` + `.arca/runbook-authoring.md`
  terminality notes.
- **Excluded:** any `failed` trigger or command, `Status` enum changes, `initialize_state` changes,
  composition/join, cycle runbook, signer identity.
- **Expected merge/output:** `passed` is written only by ordinary motion (start-in-terminal,
  arrival-at-terminal) in one atomic State File replacement; the abandoned event names the Run and
  precedes retirement; refusal never mutates.
- **Superseded-test fate:** any existing public or hidden assertion that pins `status = "planned"`
  in a state that is now terminal-passed gets the narrow lifecycle correction only (expected in
  t-062's terminal-branch fixtures and possibly t-058..t-062 hidden crates); all other oracles stay
  intact. `t051_abandon.rs` pins no event literal and should pass unchanged; if it counts
  event-line fields, it updates for the run id.

## P4 hole-poking notes (2026-08-03)

- **Would each catch a wrong answer?** PT-063-01 starts a one-Phase runbook and demands the very
  first State File carry `passed`, so a start that defers completion to a later write fails; its
  follow-up step must refuse *naming the terminal fact* and leave the whole run directory
  byte-identical, so a silent no-route refusal is not enough. PT-063-02 covers both arrival paths —
  straight line and verdict-routed branch — and requires the verdict archive to exist beside the
  passed state, so a passed write that skips consume-before-advance fails. PT-063-03 byte-compares
  the log prefix, counts exactly one `- Abandoned:` line, and requires the run id and
  `status planned` inside the event, so an event that survives as a State File value or omits the
  address fails. PT-063-04 snapshots the whole run directory across a guard refusal and then drives
  the same Run to its terminal Phase asserting `passed`, never `failed`.
- **Do they cover the edges?** A branching initial Phase (ordinary edges present) must stay
  `planned` (PT-063-02, HT-063-02); a blocked-route-only Phase counts terminal (HT-063-03); an
  obstructed event append leaves state and history byte-identical and the retry appends exactly one
  event (HT-063-04); sibling Runs stay byte-identical while another passes (HT-063-06).
- **Does each stand alone?** Yes: every case creates its own uniquely named temporary project,
  writes only its fixture, and removes it on drop. Public cases invoke the real `rtm` binary;
  hidden lanes call the `ratmac` library directly with deterministic pid+counter roots and no seed.
- **Expected red, observed red:** `cargo test -p ratmac-qa --test t063_run_completion` compiled and
  failed all four (0 passed / 4 failed): PT-063-01/02 on `planned` where `passed` is required,
  PT-063-03 on the event lacking the run id, PT-063-04 on the final terminal arrival staying
  `planned`. The hidden crate failed all six (0 passed / 6 failed): lanes 01/02/03/05/06 on the
  missing `passed` write and lane 04 on the event lacking the run id. These are the intended
  contract gaps, not fixture or compile failures.
