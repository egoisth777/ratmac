# Ticket: t-125 — checkpoint only restoration

## Vertical Outcome

The supported ticket damage and recovery mechanism resolves and records exactly one safety commit for the current reviewed green work, accepts only mutation targets tracked by that commit, and restores their index and worktree bytes only from that commit. Backup-copy, latest-file, implicit-index, arbitrary-revision, and inverse-edit restore modes are absent or explicitly refused before mutation. A stale checkpoint, untracked target, unsafe path, or unrelated unsaved work refuses by name. Interruption recovery uses the same recorded checkpoint and byte verifier. Historical evidence remains unchanged.

## Observable Output

Defined before implementation. The public checks (WCPV-016, WCPV-017,
WCPV-018) and the private lanes HT-125-01..06 both judge this shape; neither
needs the other's arrangement or the source. Every sentence below is
observable through the process exit code, stdout/stderr bytes, files under
the addressed checkout, or Git state (refs, index, worktree, configuration)
in the addressed repository. The operator is `tools/turn.ps1`, invoked as
`pwsh -File tools/turn.ps1 <verb> ...`; the verbs are `status`, `open`,
`close`, and the pair `checkpoint`/`restore` this ticket's dependency

**Terms.** The *addressed checkout*, *declared target*, *frozen manifest*,
*round-trip proof*, *clean tracked tree*, *unrelated file*, *damage*, and
`<40-hex>` are t-124's terms, unchanged. The *recorded checkpoint commit*
is t-124's term with a narrower denotation: the commit the manifest's
`commit` row names must now be the *safety commit*. The *safety commit* is
a commit whose subject is exactly the `-Item` value followed by
`: checkpoint - not a landing` (`t-125: checkpoint - not a landing` for
`-Item t-125`) - the working rules' fixed subject (SDC-002's
`t-<id>: checkpoint - not a landing`, `.arca/schema.md:510`; the item
string carries its own `t-` prefix, and the suffix's bytes are
`": checkpoint - not a landing"`). `<subject>` in a refusal is the
commit's subject verbatim - the first line of its
`git log -1 --format=%s <commit>` output, rendered empty when the subject
is empty. A *stale checkpoint* is a manifest whose recorded checkpoint
commit resolves but is not the addressed checkout's `HEAD`. *Unrelated
unsaved work* is any `git status --porcelain` row that does not start with
`??` and names at least one path that is not a manifest target (a rename
row names both its paths; it is unrelated unless every path it names is a
manifest target). A *misleading backup* is any file under `<checkout>` -
a `<target>.bak`, a `latest/` copy, an inert `<manifest>.tmp` - whose
bytes or mtime suggest a newer generation of a target; it is never a
restore source. A *declared damage row* is a non-`??` porcelain row every
one of whose paths is a manifest target.

-Item <item> -Target <path>...` runs, in this order, and performs exactly
one durable step:

   equals `<item>: checkpoint - not a landing` - the one commit this verb
   may record, resolved, never searched for in history: a tree whose
   `HEAD` carries any other subject, including another item's safety
   subject, refuses below; each target tracked as a regular file at that
   commit; a clean tracked tree. Each failure refuses below, writing
   nothing.
2. **Prove.** The round-trip proof, exactly t-124's, runs read-only
   against Git's own checkout and clean machinery; any target that fails
   it refuses before anything is written.
3. **Freeze.** Write the frozen manifest beside ticket evidence exactly as
   t-124 does: the whole file to `<manifest>.tmp`, renamed onto
   `<item-records>/<item>-checkpoint-manifest.txt` in one step, so a
   reader that finds the manifest always finds its whole content. The
   manifest format gains no row: the `commit` row records the safety
   commit's 40-hex id. An existing manifest - any generation, current or
   stale - never blocks a fresh checkpoint; the freeze replaces it in the

**Success order - `restore`.** `pwsh -File tools/turn.ps1 restore -Item
<item>` takes no `-Target` and no source of any kind: it restores exactly
the targets the frozen manifest carries, from exactly the recorded
checkpoint commit. Passing a parameter the script declares but the verb
does not use (`-Target`, `-Line`, `-Obsolete`) binds and is ignored,
exactly as today's verbs ignore parameters they do not use; a parameter
the script does not declare never reaches the tool (the
absent-restore-modes paragraph pins both). In this order:

1. **Validate.** The repository, item, and declaration guards as above;
   the manifest present and parsing to t-124's exact format; the
   manifest's `item <item>` row equals `-Item`; the recorded checkpoint
   commit resolving in the addressed repository; **`HEAD` equals the
   recorded checkpoint commit** (the stale refusal below); **`HEAD`'s
   subject is the safety subject** - re-derived from the commit itself,
   so a manifest edited to name any other revision, `HEAD` included,
   refuses even when every blob row is made to agree; every manifest
   row's path carried by that commit; every row's recorded blob id equal
   to the recomputed `git rev-parse <commit>:<path>`.
2. **Guard the tree.** After the `after-validate` pause boundary and
   before any mutation: every non-`??` porcelain row must be a declared
   damage row - target bytes mutated, staged, deleted, or renamed by the
   damage protocol are all expected - and any unrelated unsaved work
   refuses below, before the restore writes anything. This is t-124's
   post-restore dirty-tree boundary moved ahead of the mutation: what
   t-124 discovered only after overwriting targets, this contract refuses
   while everything is still as found.
3. **Restore.** Two git invocations, each one call for all targets,
   exactly t-124's: first `git update-index --add --cacheinfo
   <mode>,<blob>,<path>...` (one `--cacheinfo` per target in manifest
   order, its mode and blob read from the recorded commit) resetting
   every target's index entry to its recorded blob with no cached file
   facts, worktree bytes untouched; then the working-rules undo
   `git restore --source=<commit> --staged --worktree -- <path>...`
   (the command the damage safety rules fix byte-for-byte,
   `.arca/schema.md:513`). A non-zero exit of either refuses through
   today's shared git-failure refusal `git <arguments joined> failed:
   <text>` (`tools/turn.ps1:157`).
4. **Verify.** Exactly t-124's verification, kept: recompute the SHA-256
   of every target's worktree bytes and compare to its frozen digest;
   then require a clean tracked tree. Both must hold: a clean tracked
   tree alone cannot pass a target whose bytes differ, and matching
   digests alone cannot pass a dirty index or tracked tree. Nothing is
   deleted on failure and no unrelated file is touched: the restore's
   writes are limited to the manifest's own target paths, so a smudge
   filter or line-ending conversion that dirties or rewrites bytes is
   caught by digest or by the clean-tree check - never by collateral
   damage.

**Checkpoint-only: the absent restore modes.** Five restore modes are
absent, and where an input tries to reach one it refuses before mutation:

- *Backup-copy and latest-file*: no parameter or manifest field names a
  backup path or a newest-file source; the manifest format has no such
  row, so an added row is the malformed refusal and an edited `commit`
  row hits the stale, safety, path, or blob rows above. A misleading
  backup is never read: its bytes and mtime are byte-identical before and
  after every invocation, success or refusal - both suites hash them.
- *Implicit-index*: the restore's `git restore` command is pinned with
  `--source=<commit> --staged --worktree`, preceded by t-124's
  recorded-blob index reset that defeats the stat cache; the tool never
  runs `git restore <paths>` or `git checkout -- <paths>`. Observable:
  damage staged into the index (`git add` of red target bytes) plus
  worktree mutation is fully undone - the restored worktree bytes equal
  the frozen digests, not the staged red bytes, and the index is
  clean; under any index-sourced mode the staged red bytes would land
  in the worktree and the digest check would refuse.
- *Arbitrary revision*: restore takes no revision. The manifest is the
  only source of the commit, and it is accepted only when that commit is
  `HEAD` (stale row) and carries the safety subject (safety row), so
  editing the manifest to point at any other revision - tip, older
  generation, `HEAD~1`, a tag - refuses by name before mutation. On the
  command line, every parameter the script does not declare - named or
  bare positional - is rejected by PowerShell parameter binding before
  the script body runs (the script is an advanced script,
  `[CmdletBinding()]` at `tools/turn.ps1:97`, declaring exactly `Verb`,
  `Item`, `Line`, `Obsolete`, `Target` (t-124's, comma-splitting), and
  `Force`, `tools/turn.ps1:98-116`): exit 1, stdout empty, no
  `turn refused;` line, no repository read or write, stderr carrying the
  shell's own
  binding error naming the script and the parameter name (`turn.ps1:
  A parameter cannot be found that matches parameter name '<name>'.`)
  or the argument (`turn.ps1: A positional parameter cannot be found
  that accepts argument '<arg>'.`). Both are platform facts of the
  invocation, not tool refusals - and either way no revision ever
  reaches the tool: `restore -Item <item> -Revision <anything>`,
  `-Source <anything>`, `-Backup <anything>`, and a bare `<rev>` all
  die at the shell, and no source-naming parameter exists for a caller
  who binds correctly.
- *Inverse edit*: the tool writes no hand-computed inverse of the damage;
  its only mutation of the worktree is the one pinned `git restore`
  invocation, so the restored bytes are the recorded blobs or a refusal -
  never a reconstruction.
- *Copy-back fallback*: recovery never copies files from anywhere else;
  the recovery table below repeats the same recorded checkpoint and the
  same two commands (index reset, then restore), and its verifier
  re-derives every frozen hash.

**The recorded generation wins (WCPV-016).** With two source generations
in play - generation one frozen at safety commit `<X>`, then the damage
restored, then further green work committed under the same subject as
safety commit `<Y>` and re-checkpointed (the manifest now records `<Y>`,
replacing `<X>` in the one rename), and a misleading backup holding
newer-looking bytes planted anywhere under `<checkout>` - a supported
`restore` selects exactly `<Y>`'s bytes: every target's recomputed digest
matches its frozen digest, the index and tracked tree are clean, and the
backup's bytes and mtime are unchanged. The stale twin: a manifest left
recording `<X>` while `HEAD` is `<Y>` refuses the stale row above with
both ids, writing nothing. No restore ever selects bytes by recency:
recency is not an input anywhere in the verbs.

**Recovery and restart.** Killing the invocation at any point is the
interruption fixture; the damage protocol is single-operator and the verbs
hold no lock, so nothing waits and nothing deadlocks. An `index.lock` left
by a killed git child makes the next git call fail with Git's own text
through the shared git-failure refusal; removing it is the operator's act
- the tool never deletes a lock, a ref, or a directory. t-124's recovery
table holds with its third row (kill before the index reset) extended
to name the `after-validate` pause and the guards a fresh run re-checks,
its fourth row (kill after the index reset, before `git restore`) kept
as landed, and the last two added:

| State found after a kill | The repeated command |
| :--- | :--- |
| No manifest (kill before the freeze rename) | `checkpoint` runs fresh from the same clean tree; an inert `<manifest>.tmp` may remain and is replaced. |
| Manifest durable (kill after the freeze rename) | `restore` may proceed; a repeated `checkpoint` from the same clean tree rewrites byte-identical manifest bytes. |
| Restore killed before the index reset (including at the `after-validate` pause) | Nothing was written; `restore` runs fresh - including re-running the stale, safety, and unrelated-work guards against whatever state the kill left. |
| Restore killed after the index reset, before `git restore` | Each target's index entry holds its checkpoint blob with no cached file facts, its worktree bytes untouched; `restore` re-runs both commands and verifies. |
| Restore killed during or after `git restore` | Targets hold checkpoint bytes, unverified; `restore` re-runs the identical commands and verifies - it is idempotent and never claims success without verification. |
| Restore killed after verification | The operation is complete; a repeated `restore` re-verifies and prints the success report. |
| Checkpoint amended into the landing (`git commit --amend`, SDC-003) with the manifest still present | `restore` refuses the stale row - `HEAD` moved; the recorded checkpoint is never applied onto the folded landing. |
| A damage check interrupted mid-check, then restored and verified | The same manifest stays current - `HEAD` never moved - so the next damage check needs no new checkpoint: mutate, then `restore` again, which re-derives every frozen hash; an operator who prefers a fresh freeze gets the byte-identical manifest from the recovery row above. |

**Settings are never changed.** No verb writes global or repository Git
configuration: `.git/config`, the global configuration file, and
`git config --global --list` are byte-identical before and after every
invocation, success or refusal - both suites hash them. Effective-settings
drift is detected (round-trip refusal before damage; digest-mismatch
refusal after restore), never repaired. The historical counterexample is
the contract's own fixture: under `core.autocrlf=true` a
`git restore --source=<checkpoint> --staged --worktree --` left
`git status --porcelain` empty while the restored bytes differed from the
frozen digests - exactly what the digest-mismatch refusal now catches by
path.

**History is never changed.** No verb creates a commit, moves a ref, or
touches any historical evidence: `.arca/log.md`, every archive under
`.arca/issue/archive/`, `.arca/residual/archive/`, and
`.arca/ticket/archive/`, every other file under the item-records root
including `<item>.md` itself, and the Engine root are byte-identical
before and after every invocation - the manifest file is the one byte any
verb ever writes, and it is a new untracked file beside the item record,
never an edit of an existing one.

**No operation log.** As t-124: the turn tool writes no operation log and
gains none; the ordered stdout lines above are the observable order, and
a refusal prints no success line. The Engine's operation-log feature and
its kinds are untouched.

**Test-only seams.** t-124's one pause seam is reused unchanged - the same

one-verb ownership, the same `RATMAC_TEST_TURN_PAUSE_MARKER`,
