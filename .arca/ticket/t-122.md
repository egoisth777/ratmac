# Ticket: t-122 — successor ownership

## Vertical Outcome

A spawned replacement becomes available to public Run operations only after its owning parent ledger durably records its identity, class, bindings, workspace, and superseded Run. Concurrent step, spawn, hold, abandon, join, and roster reads must never observe an admitted successor without that ownership. Root-before-Run lock order and root-lock-free guard evaluation remain unchanged. Failed or interrupted replacement preserves the predecessor or records a complete recoverable replacement; an ambiguous write never causes deletion of potentially owned evidence, and identifiers are never reused.

## Observable Output

Defined before implementation. The public checks and the private lanes both
judge this shape; neither needs the other's arrangement or the source. Every
sentence below is observable through the process exit code, stdout/stderr
bytes, files under the Engine root, or the operation log the crate feature
`test-fault-injection` writes. Paths in messages use the Engine's one
displayed spelling (forward slashes); `<Engine root>` below is that spelling
of the resolved shared `.ratmac/`.

**Terms.** A predecessor is *ledger-recorded* when a roster member's
`spawn-ledger` parses to an entry whose `id` names it, and *top-level*
otherwise. A Run is *admitted* when `<Engine root>/runs/<id>/run.toml`
exists, and *usable* when public Run operations may address it - exactly the
`runs/` directory members the roster lists. A *recorded successor* of a
predecessor is a parseable entry in the owning parent's `spawn-ledger` whose
`supersedes` names that predecessor and whose `abandoned` mark is not set. A
successor a human has since abandoned is terminal like any abandoned Run: it
is no recorded successor, it is never admitted again, and its id is never
reused.

**Publication order - a ledger-recorded predecessor.** The invariant: the
successor never becomes usable or rendered as top-level before its parent
ledger entry is durable, and at every instant at most one of predecessor and
successor is usable. `rtm respawn --run <predecessor> --confirm "respawn
<predecessor>"` therefore performs exactly three durable steps, in this
order:

1. **Record.** Before anything is written, take the root lock and then the
   predecessor's Run lock with today's `acquire_root_then_run` - it waits
   for the Run's availability only while root is released, never while
   holding root, under the existing 5 s deadline whose expiry refuses
   today's `lock wait expired: <path>; <owner-token diagnostic>` - then
   claim the successor's Run lock without waiting under the held root. No
   parent Run lock is taken (today's respawn takes none; a parent `step`
   already revalidates the ledgers its guards read before mutating). Hold
   the root, predecessor, and successor locks from this step through
   admission. Before any `runs/` directory exists for the successor:
   reserve the successor id in `mint.toml` (a reserved ordinal is
   never reused, exactly as a failed mint reserves its ordinal today); refuse
   first when `<Engine root>/runs/<successor>` already exists (any file
   type); then append the successor's entry - its id, the predecessor's
   recorded class and bindings, `spawned_at`, the predecessor's recorded
   workspace, `abandoned = false`, `supersedes = <predecessor>` - to the
   owning parent's `spawn-ledger`. A failed append is classified exactly as
   spawn's append is today (the four aftermath classes below); the
   predecessor is still live at this boundary, so every append failure
   leaves it untouched.
2. **Retire.** Retire the predecessor through the abandon path - flip its
   entry's `abandoned` mark in the same ledger, append its terminal event to
   the transition log, retire its admission state, evidence, and lock, keep
   its reserved directory with its `spawn-ledger` - exactly the retirement
   `rtm abandon --run <predecessor> --confirm "abandon <predecessor>"`
   performs - applied here under the already-held locks, never by acquiring
   root again while a Run lock is held; respawn supplies the abandon phrase
   internally, as today.
3. **Admit.** Create `<Engine root>/runs/<successor>/` holding exactly the
   bytes a fresh mint writes: `run.toml` (the recorded class's initial
   State and status), `evidence.toml` (engine identity, goal baseline,
   runbook pin), and a reserved empty `spawn-ledger`. The instant
   `run.toml` lands the successor is admitted, usable, and already owned by
   the durable entry of step 1. `run.toml` is written last, after
   `evidence.toml` and `spawn-ledger`, so an interrupted admission never
   leaves an admitted successor with missing or unchecked artifacts.

The three locks taken before the record step are held through retirement
and admission and released only after admission or a refusal: record, retire,
and admit are one root-locked decision, and nothing ever acquires the root
lock while a Run lock is held. No Run lock is ever awaited while root or
another Run lock is held - the predecessor is claimed root-first before the
successor claim, `acquire_root_then_run` waits only while root is released,
and the successor claim never waits. There is no instant at which both Runs
are usable: before the record step the successor does not exist; after it and
before retirement only the predecessor is usable; between retirement and
admission neither is; after admission only the successor.

**What each operation observes at the boundaries.** B1 = the entry is
durable and the predecessor still live (retirement and admission pending);
B2 = the predecessor retired and the successor not yet admitted; B3 =
admitted (the completed state, unchanged from today's completed state). A
live invocation holds the root lock and the predecessor's and successor's
Run locks at both B1 and B2, so each operation below either reads lock-free
or waits on a held lock; a wait that outlasts the existing 5 s deadline
refuses with today's `lock wait expired: <path>; <owner-token diagnostic>`
and writes nothing.

| Operation | At B1 | At B2 | At B3 |
| :--- | :--- | :--- | :--- |
| `rtm status`, `rtm doctor` (lock-free record readers) | Summary line lists no successor. Predecessor's row is its ordinary live row. The successor renders one row: `run-005: child of run-001; class <recorded class>` (plus the inherited `bind ...` clause when the predecessor recorded one) `; supersedes run-002; not on the roster (<Engine root>/runs/run-005 is absent)`. `rtm doctor` exits 0; `rtm status` keeps today's exit code and first line for the form invoked - only its rows change as described. | Same successor row; the predecessor's row keeps its role fields and now ends `; retired`. | Successor's row reads its role fields (ending `supersedes run-002`) then its State and status; predecessor's row `retired`; both as today. |

| The join guard (inside `rtm step --run <parent>`; the parent's lock is not held) | The guard's ledger and disk reads are lock-free and refuse `ledger children missing on disk: run-005; the expected set never silently shrinks` - the successor is recorded but not on disk, so the expected set never silently shrinks. | Same. | Judges the successor's own status, as today. |

At B1 and B2 the successor is exactly as usable as an id never minted: every
public Run operation refuses it by address, the roster summary never lists it,
and it is never rendered top-level, because the ledger entry is durable before
any `runs/` presence exists. `rtm doctor` reports the same facts from the same
records - a B2 predecessor `retired`, a B1/B2 successor absent with its
role recorded - changing nothing.

**Success output.** A completed respawn - fresh, or finished by recovery -
prints stdout exactly as today, one LF-terminated line, exit 0, stderr empty
unless the warning below fired:

```
rtm: run superseded; successor run run-005 minted at .ratmac/runs/run-005/
```

**Failure boundaries - a ledger-recorded predecessor.** Every refusal: exit
1, stdout empty, stderr `rtm: respawn refused; <text>`. `<ledger path>` is
the displayed parent `spawn-ledger` path. Nothing deletes potentially owned
evidence: the only removals respawn ever performs are the top-level path's
prove-then-delete rollback below and the abandonment retirement itself.

| Boundary | stderr text after `rtm: ` | Remains on disk | Route |
| :--- | :--- | :--- | :--- |
| Successor address occupied (checked under the root lock after reserving the id) | `respawn refused; respawn cannot reserve the successor address <Engine root>/runs/run-005: the path already exists; remove or repair it, then retry` | Predecessor untouched and live; ledger unchanged; `mint.toml` reserves run-005. | Clear or repair the path, repeat; the retry mints a fresh id beyond the reserved high-water. |
| Append classified `AbsentAfterError` | `respawn refused; respawn cannot record the successor entry for run-005: <error>; nothing was admitted and run-002 keeps its admission state; the reserved id run-005 is never reused; repeat this command to respawn with a fresh id` | Predecessor live; ledger bytes unchanged; no successor directory; ordinal reserved. | Repeat respawns with a fresh id (nothing was recorded). |
| Append classified `RecordedAfterError` | No refusal: stderr gains today's warning `warning: successor ledger append for run-005 reported <error>, but <ledger path> records the complete entry; treating the successor as committed`, and the run proceeds to steps 2 and 3 (exit 0, the success line above). | - | - |
| Append classified `Indeterminate` | `respawn refused; respawn cannot determine whether its successor entry committed for run-005: <detail>; nothing was admitted and run-002 keeps its admission state; the ledger <ledger path> was left exactly as it now reads; inspect it before retrying` | Ledger bytes left as they are; predecessor live; no successor directory. Never a deletion. | Repair the ledger (a partial trailing entry makes the strict read refuse by name); a repeat then records or finishes honestly. |
| Retirement refusal (after the entry is durable) | `respawn refused; respawn interrupted retiring run-002: <refusal>; the successor run-005 is recorded in <ledger path> and not yet admitted; repeat this respawn command to finish it` | Predecessor live and unretired (the abandon path's own refusal leaves it so); the complete recoverable replacement is recorded; no successor directory. | Repeat the same command; it finishes the recorded operation. |
| Admission failure | `respawn refused; respawn cannot admit the recorded successor run-005: <error>; run-002 is retired and <ledger path> records run-005; repeat this respawn command to finish it` | Predecessor retired; entry durable; a partial `runs/run-005/` may exist and is never deleted. | Repeat the same command; admission is idempotent. |
| Ledger records more than one successor of the predecessor | `respawn refused; the spawn ledger <ledger path> records more than one successor of run-002; exactly one recorded successor may be finished; repair the ledger, then retry` | Everything as found. | Human ledger repair; the strict read keeps refusing until unique. |
| Another invocation is completing the recorded successor | `respawn refused; run run-002 already has its recorded successor run-005 in <ledger path>; another invocation is completing it; repeat this command after that invocation finishes or fails` | Whatever the active invocation has durably done so far. | Defensive only, observed by neither suite: no public command can hold an unadmitted successor's Run lock - each refuses a Run with no Run Record before taking any lock - and a live respawn holds root, so a repeat waits at root instead. The row exists so a failed no-wait successor claim refuses instead of waiting; retry after the claim releases. |

A validation refusal - residue, missing or wrong confirmation, unknown run,
undeclared recorded class, unreadable ledger - keeps today's exact texts and
codes and writes nothing, as today.

**Recovery - finish or cancel the recorded operation, never a duplicate.**
The repeated command `rtm respawn --run <predecessor> --confirm "respawn
<predecessor>"` decides from the records, never mints a new id while a
recorded successor exists, and never reuses any ordinal:

| State found | The repeated command |
| :--- | :--- |
| Predecessor live, no recorded successor | A fresh respawn: reserve, record, retire, admit, with a fresh id. |
| Predecessor live, one recorded successor, its Run lock claimable | Finishes it: retire the predecessor, admit that same id, print the success line naming it. |
| One recorded successor, not admitted, its no-wait Run claim fails (predecessor live or retired) | The defensive mid-flight refusal above; nothing is written. |
| Predecessor retired, one recorded successor, not admitted | Admits that same id (no retirement to redo) and prints the success line naming it. |
| Predecessor retired, one recorded successor, already admitted | Today's already-terminal refusal; the operation is finished. |
| Predecessor retired, no recorded successor (including every top-level predecessor) | Today's already-terminal refusal, unchanged. |
| More than one recorded successor | The ambiguity refusal above. |

Admission is restartable: artifacts already present and byte-identical are
kept, missing ones are written, and a conflicting byte refuses with the
admission-failure row above, its `<error>` naming the conflicting path,
deleting nothing. An unadmitted successor's lock left by a killed
process is not an obstacle: Run locks are kernel claims that die with their
process, so the repeated command claims the recorded successor and finishes.
An interrupted respawn may also be handed to a human retirement: after a kill
at B1 the predecessor is live, so `rtm abandon --run <predecessor> --confirm
"abandon <predecessor>"` succeeds exactly as today, and the repeated respawn
then finds the predecessor retired with the recorded successor unadmitted
and admits it.

**Two concurrent respawns of one predecessor.** The root lock serializes
the whole decision: exactly one invocation records the successor entry, and
it is the only invocation that ever admits a successor for that predecessor.
A second invocation waits at the root lock - it never acquires root while
holding a Run lock - and past the 5 s deadline refuses with today's
wait-expired text, writing nothing; after the winner's root release it meets
the already-terminal refusal (the winner completed), finishes the one
recorded successor (the winner refused after recording), or respawns freshly
(the winner refused before recording). The mid-flight refusal is defensive
only, as its failure row describes. An admitted successor's Run lock held by
any command never changes the answer for its retired predecessor: the
already-terminal refusal is decided before any lock. No deadlock: every
acquisition is root-before-Run; the predecessor's lock is taken by
`acquire_root_then_run`, which waits only while root is released; the
successor's Run lock is only ever claimed without waiting while root is
held; no Run lock is ever awaited while root or another Run lock is held.
The root lock is never held while guards run: respawn evaluates no guards,
and the abandon retirement it applies under its held locks runs none (its
checks are file reads); `step` keeps evaluating guards under only the
addressed Run lock.

**A top-level predecessor stays as today.** With no owning parent ledger the
contract above has nothing to record, so nothing changes: validate; mint the
full successor under the root lock (`runs/<successor>/run.toml` exists from
the mint on, so the successor is usable and rendered top-level during
retirement, exactly as today); retire the predecessor through the abandon
path; write no ledger entry; print the same success line. A retirement
refusal rolls the minted successor back with today's prove-then-delete
semantics and today's texts (`respawn interrupted retiring run-002:
<refusal>; the successor mint was rolled back`, and the incomplete-rollback
variant). This is a deliberate scoping, not an omission: WRS-001 binds a
successor to its owning parent ledger's durable record, and a top-level
replacement has none.

**Unchanged behavior that stays green.** The confirmation contract and every
existing refusal text and exit code (missing `--run`, missing and mismatched
`--confirm`, unknown run, already-terminal, undeclared class, and the CLI
argument errors); workspace, class, and binding inheritance from the recorded
entry (the invoking checkout only for a top-level predecessor); the
`supersedes` link in the entry and the roster row; the one-level spawn cap;
the append-only ledger (prior bytes stay a prefix; the only rewrite is the
abandoned-mark flip); root-lock-free guard evaluation; `rtm respawn --help`;
`Scheduler::respawn` and `cli::run_from` parity; reserved ordinals never
reissued; the mint counter untouched by every pre-mint refusal.

**Operation log.** With `test-fault-injection` and
`RATMAC_TEST_OPERATION_LOG` set, a respawn records only the existing kinds
`roster`, `record`, `ledger`, `runbook`, `target`, and `lock` - never
`blocker`, and no new kind. `target` stays exactly where the landed WEBV-014
rule marks it today: the existence check of the recorded workspace, a
validation mark before the first `lock`. No `lock` line precedes the
validation marks: the
first `lock` opens the recording step. In one successful ledger-recorded
respawn the marks order by stage: the successor-append `ledger` marks; then
the predecessor's abandoned-mark `ledger` and terminal-event `record` marks;
then the successor's admission `record` marks, with its reserved
`spawn-ledger` `ledger` mark last. Exact per-call
counts are not part of this contract; the kinds and that stage order are. A
refusal records only the boundaries it reached, and every validation refusal
precedes the first `lock`.

**Fault injection and pauses**, compiled only with feature
`test-fault-injection`; unset, empty, or unrecognized values - or a build
without the feature - change nothing, and each fires at most once per
invocation at the first boundary it names:

- `RATMAC_TEST_RESPAWN_FAULT`, one of:
  - `ledger-append` - the successor append reports
    `injected successor-ledger append failure` with no bytes written (the
    `AbsentAfterError` row);
  - `ledger-append-committed` - the complete entry is written and synced,
    then the append reports the same error (the `RecordedAfterError` row:
    warning, exit 0);
  - `ledger-append-partial` - half the rendered entry bytes are written, then
    the error (the `Indeterminate` row);
  - `retire` - the retirement step refuses `injected respawn fault at retire`
    (carried by the retirement-refusal row's `<refusal>`);
  - `admit` - the admission refuses `injected respawn fault at admit`
    (carried by the admission-failure row's `<error>`).
  On the top-level path only `retire` has a boundary; the other values are
  no-ops there.
- `RATMAC_TEST_RESPAWN_PAUSE`, one of `after-record` (B1: entry durable,
  predecessor live, tail not started) or `after-retire` (B2: predecessor
  retired, successor unadmitted). At either boundary the paused invocation
  holds the root lock and the predecessor's and successor's Run locks, so
  every wait above is a wait on this pause. Requires
  `RATMAC_TEST_RESPAWN_PAUSE_MARKER`
  and `RATMAC_TEST_RESPAWN_PAUSE_RELEASE` (file paths) and a positive integer
  `RATMAC_TEST_RESPAWN_PAUSE_TIMEOUT_MILLIS`; a missing or invalid companion
  refuses naming it, checked when the respawn starts - before any lock or
  write - so that refusal writes nothing. At the boundary respawn writes the
  boundary name and a newline to the marker path in one step, so a reader
  that finds the marker file always reads that whole line, then waits until
  the release path exists; on timeout it refuses
  `rtm: respawn refused; injected respawn pause at
  <boundary> expired`, exit 1, leaving exactly the boundary's disk state.
  Killing the paused process at either boundary is the interruption fixture;
  the recovery table above decides the repeat.
- Existing seams stay reusable beside these: `RATMAC_TEST_LOCK_HOLD` with
  `RATMAC_TEST_LOCK_MARKER`, `RATMAC_TEST_LOCK_RELEASE`, and
  `RATMAC_TEST_LOCK_HOLD_TIMEOUT_MILLIS` to hold the root or a Run domain and
  race a boundary; `RATMAC_TEST_LOCK_FAULT` to fail a domain acquisition;
  `RATMAC_TEST_OPERATION_LOG` for the marks above; and a read-only parent
  `spawn-ledger` (the HT-066 device) as a real-I/O `AbsentAfterError`.
