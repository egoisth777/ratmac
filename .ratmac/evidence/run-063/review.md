# Independent review before full proof

Accepted on 2026-10-30, before executing the final full workspace proof.

- Four independent reviewers worked from the implementation as reviewed, under fixed rules: read only; nothing edited, created, deleted, built, or run in the ticket worktree, its reviewed copy, the copy of the lanes before the move, or the primary checkout; no lane run, because the lane-sweep lane's `t-094` runs share one fixed folder in the system temp folder and the coordinator's timed runs were going on; a behaviour probe only inside a fresh temporary folder, with a small fixture of the reviewer's own, deleted afterward. The helper reviewer took the locked-folder helper in `test/qa/src/baseline.rs`; the lane reviewer took the move of the 25 private lanes onto it, 46 changed files across `t-084`, `t-085`, `t-086`, `t-108`, `t-112`, `t-113`, `t-115` to `t-123`, `t-126` to `t-130`, `t-132` to `t-135`, and `t-137`; the public reviewer took `svev_007` and `svev_008` in `test/qa/tests/t139_same_lane_verdict.rs`; the private reviewer took the new private lane crate, HT-139-01 to HT-139-06.
- `lane_folder(lane, CARGO_TARGET_TMPDIR)` answers the folder `<CARGO_TARGET_TMPDIR>/<lane>` and holds the standard library's exclusive file lock on `lane.lock` inside it from the first call in a process until the process ends. A call that has to wait first writes one line naming the lock file straight to standard error, past the test harness's capture - `<lane>: waiting for the lane lock <lock file>`. Later calls in the same process answer the same folder without waiting, however its path is spelled. `LaneFolder::engine`, `build`, `cargo`, and `test` hand Cargo that folder as both `--target-dir` and its build folder (`build.build-dir`), on the command line only. A child the run starts with the folder's grant (`RATMAC_SUPPORT_LANE_GRANT`, which `support::command` drops from every environment it inherits) uses the folder without taking the lock while some process holds it. A drive-letter folder loses Windows's long-path marker `\\?\`, because `cmd.exe` cannot start a program spelled with it. The 25 lanes run every Cargo build and test on the repository or on another lane's crate through it; the frozen before-source corpus under `test-hidden/t-126/fixtures/before/` is untouched.
- The helper review took five rounds. The first rejected with one medium finding: the helper wrote each lock it took into the process's own environment and then skipped the lock for any listed file without checking that anyone held it, so every child inherited the exception - SVE-007 allows none, and changing the parent's environment conflicts with WCP-002. Its four lows were path spellings counted as different folders, a refused Engine build retried on every call, a configured build folder left in place by `--target-dir` alone, and a description that called four methods one path. All were fixed: the grant replaced the environment list, folders are keyed by their resolved path, the first build's answer is kept, and the build folder is passed too. The second round accepted with two lows - comments promised more than the grant checks, and a `{` or `}` in the folder path failed every call because Cargo reads braces in `build.build-dir` as template variables - fixed by corrected comments and a refusal that names such a folder. The third round accepted with no finding, the fourth with one low comment claim about network paths, fixed in comments, and the fifth accepted the final bytes with no finding.
- The lane review first rejected with one medium finding - `t-126/Cargo.toml` took `ratmac-qa` as a normal dependency instead of a test-only one, which WCP-002 forbids - and one low: two HT-137-06 checks could no longer fail. Both were fixed, and the renewed review of those two files accepted with no finding.
- The public review took four rounds. The first rejected with one high finding - the held-lock step could not tell a run that waits from one that prints the wait line and builds anyway - and three mediums: a lane that lets its lock go right after taking it still passed `svev_008`; the checks were not kept apart from other processes through `t-094`'s fixed `linked-t094` folder; and the inventory did not count a `lane_folder` call handed a folder inside the repository. The second rejected with one medium - on Windows a failed run left its scratch copy of about 4 GB behind while the header said otherwise - and two lows. The third accepted with two lows, and the fourth accepted the comment-only fix of one of them with no finding. The other low stays open as recorded and is filed as a wish: the sweep step has no deadline of its own, and on Windows the sweep tool's time limit does not stop a lane whose test executable holds the output pipe.
- The private side took two reviews. The first rejected; the lane writer's notes keep its findings' severity only for one high - HT-139-05's check that nested builds stay in the lane folder could never fire - and two mediums: `t-137` was missing from HT-139-01's identity table, and HT-139-04 killed its run after the build, never during it, and never checked where the build output lands. The writer made twelve repairs, those three included: HT-139-05 also runs `t-084` and fails on any nested `rtm`, `edition-cut`, or `snapshot-manifest` file outside the lane folder; HT-139-06 records both build-folder variables in `t-108`'s run of `t-094`; HT-139-03 exercises the grant; HT-139-01 no longer reads the tracked sweep report; every pause loop gives up after ten minutes and ending a run kills its process tree on Windows; wait lines are read from both output streams. Two later changes followed: the header leaves HT-139-01's "the lane sweep reads each lane green" clause to the full sweeps and `check` (LNR-003), as the ticket records, and HT-139-04's kill is judged by its outcome, with a give-up marker, after the coordinator's stress runs found `taskkill`'s exit status unreliable on a busy machine (8 of 8 copies passed on a quiet machine, 15 of 16 failed beside 64 busy processes; after the fix 16 of 16 passed for the writer and 16 of 16 for the coordinator). The renewed private review accepted with eight low findings, open as recorded: HT-139-01's before-and-after hash repeats a build `t-086` already made, so that clause rests on HT-086-04, as the header says; HT-139-06 can collide with another `t-094` run through `linked-t094`; the crate's own direct builds in HT-139-01 and HT-139-05 inherit the host's build-folder variables; HT-139-03's first wait includes a fresh fixture build; no grant names a different lock file; HT-139-05 never shows a stand-in recording its own launch; a lock released when the calling test returns, and a build that passes the folder through the process environment, each pass every row; and the header's process-tree claim holds on Windows only.
